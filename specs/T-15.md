# T-15 — Conductor handoff latency: wake on transition instead of the 60 s pass

> Frozen spec. An implementer completes this without making design decisions.
> If something here is wrong or missing, the implementer stops and reports; they do not improvise.

## Goal

The conductor runs a pass the moment a task crosses one of its four handoffs (claimed, implemented,
validated, integration passed) instead of waiting for the next tick of its interval. Today `muthur sim run`
shows scripted sessions taking about two seconds while each task waits on the interval at each handoff; at
the production 60 s interval that is four to five minutes per task before any model thinks. After this task
the interval is only the fallback for anything the wake-up misses (lease expiries, cooldowns, a hub that
restarted with work already waiting).

## Context

- `src/Muthur.Server/Services/ConductorService.cs` — `ConductorService.RunPassAsync` is one pass; it is
  idempotent, refuses to overlap itself (`_pass.WaitAsync(0)` returns 0 when a pass is already running), and
  is called today only by `ConductorWorker` at the bottom of the same file. `ConductorWorker` is a
  `BackgroundService` whose loop is: run a pass, then `Task.Delay(EffectiveConductorIntervalSeconds, clock)`.
- `src/Muthur.Server/Services/Ledger.cs` — every committed mutation publishes its recorded events on
  `EventFeed` (`feed.Publish(mutation.Recorded)`) after the transaction commits. That is the only place a
  transition becomes visible and it is already decoupled from the services that write it.
- `src/Muthur.Server/Services/EventFeed.cs` — `Subscribe(Action<IReadOnlyList<LedgerEvent>>)` returns an
  `IDisposable`. Subscribers are called synchronously on the mutating thread and must be cheap and never throw.
- `src/Muthur.Server/Infrastructure/Startup.cs` — `ConductorService` is a singleton; `ConductorWorker` is a
  hosted service registered only when `MuthurOptions.BackgroundServices` is true (false in tests).
- `src/Muthur.Server/MuthurOptions.cs` — `ConductorIntervalSeconds` (default 60) and
  `EffectiveConductorIntervalSeconds` (floor 15). Unchanged by this task.
- Time comes from the injected `TimeProvider`. `Task.Delay(TimeSpan, TimeProvider, CancellationToken)` is
  the pattern already used by the worker; tests drive it with `HubFactory.Clock` (a `FakeTimeProvider`).
- The event types that are the four handoffs, exactly as recorded today:
  - `task.claimed` (`TaskService`, line ~122) — an orchestrator took a backlog task; the conductor's next
    pass accounts for the slot and can staff the next thing.
  - `task.implemented` (`LifecycleService.ImplementedAsync`) — the task is `validating`; a validator can be staffed.
  - `task.validated` (`LifecycleService`, two sites: the no-validators short-cut and the last verdict) — the
    task can be handed to integration or landed.
  - `integration.passed` (`IntegrationService.Complete` via `Record(m, c, "passed")`) — the task can be landed.
- Tests: `tests/Muthur.Server.Tests/ConductorTests.cs` shows the fixture pattern (`HubFactory` with
  `Muthur:ConductorEnabled = true`, `TestRepo`, `_hub.Validators` / `_hub.Orchestrators` fakes).
  `tests/Muthur.Server.Tests/Eventually.cs` is the only sanctioned real-time wait (a hang-detector budget).
  Tests never sleep to synchronize.
- `src/Muthur.Cli/Commands/SimCommands.cs` — `sim run` sets `Muthur__ConductorIntervalSeconds` to `5` and
  prints "the conductor looks every 5s". Both are wrong today: the floor makes the effective interval 15 s.

## Non-goals

- No change to `ConductorIntervalSeconds`, its floor, or the `ConductorStatusDto` / CLI `conductor status`
  output. No new ledger event type for a wake-up (one per transition would double the ledger's noise for
  nothing a `conductor.staffing` event does not already say).
- No debouncing or batching window. Passes are cheap and already refuse to overlap; an extra pass is
  harmless, a missed one is the bug.
- No wake-up for other event types (`task.added`, `task.released`, `task.dependencies_ready`,
  `task.validation_failed`, heartbeats, messages). Only the four handoffs above.
- No changes to `ConductorService.RunPassAsync` itself or to what a pass does.

## Design

### `ConductorWake` (new, `src/Muthur.Server/Services/ConductorWake.cs`)

```csharp
/// <summary>
/// What gets the conductor out of its chair between passes: a task crossing one of the handoffs it staffs.
/// Subscribed to the ledger's event feed for the life of the hub; the worker waits on it with the pass
/// interval as the fallback.
/// </summary>
public sealed class ConductorWake : IDisposable
{
    /// <summary>The event types that are a handoff the conductor acts on. Nothing else wakes it.</summary>
    public static readonly IReadOnlySet<string> Transitions =
        new HashSet<string>(StringComparer.Ordinal) { "task.claimed", "task.implemented", "task.validated", "integration.passed" };

    public ConductorWake(EventFeed feed, TimeProvider clock);

    /// <summary>
    /// Records that a pass is wanted. Idempotent while one is pending: any number of transitions before the
    /// next wait collapse into one wake-up, and a transition that lands during a pass is kept for the wait
    /// that follows it, never lost.
    /// </summary>
    public void Nudge(string reason);

    /// <summary>
    /// Completes with the reason of the pending nudge as soon as there is one (immediately, if a nudge arrived
    /// before the call), or with null once <paramref name="fallback"/> has elapsed on the clock. Consumes the
    /// pending nudge. One waiter at a time: the worker is the only caller.
    /// </summary>
    public Task<string?> WaitAsync(TimeSpan fallback, CancellationToken ct);

    /// <summary>Whether a nudge is waiting to be consumed. For tests and status only.</summary>
    public bool Pending { get; }

    public void Dispose();   // unsubscribes from the feed
}
```

Behaviour, exactly:

- The constructor subscribes to `feed`. The handler scans the batch; if any event's `Type` is in
  `Transitions` it calls `Nudge(type)` once with the first matching type and returns. It never throws
  (the feed swallows exceptions, but a wake-up must not depend on that).
- State: a lock, a `string? _pending` (the reason, null when nothing is pending) and a
  `TaskCompletionSource<string?>? _waiter` (the current wait, if one is parked). Create the TCS with
  `TaskCreationOptions.RunContinuationsAsynchronously` so a mutation thread never runs the worker's
  continuation inline.
- `Nudge(reason)`: under the lock, if a waiter is parked, take it out and complete it with `reason` (outside
  the lock); otherwise set `_pending ??= reason` (the first reason wins; do not overwrite).
- `WaitAsync(fallback, ct)`: under the lock, if `_pending` is set, clear it and return it completed. Otherwise
  park a new TCS as `_waiter`. Then race it against `Task.Delay(fallback, clock, ct)`:
  - waiter wins → return its result;
  - delay wins → under the lock clear `_waiter` (only if it is still this TCS) and return null;
  - `ct` cancels → clear `_waiter` the same way and throw `OperationCanceledException` (the delay already does).
  A nudge that arrives after the delay won but before `_waiter` is cleared must still be honoured: `Nudge`
  completing the TCS is fine because `WaitAsync`, on the delay branch, checks whether the TCS was completed
  (`_waiter.Task.IsCompletedSuccessfully`) and if so returns its result instead of null.
- `Pending` reads `_pending is not null` under the lock.
- `Dispose` disposes the subscription. Idempotent.

### `ConductorWorker` (modified, bottom of `ConductorService.cs`)

- Add a `ConductorWake wake` primary-constructor parameter (after `clock`, before `logger`).
- Replace `await Task.Delay(TimeSpan.FromSeconds(options.EffectiveConductorIntervalSeconds), clock, stoppingToken);`
  with `var reason = await wake.WaitAsync(TimeSpan.FromSeconds(options.EffectiveConductorIntervalSeconds), stoppingToken);`
  and, when `reason` is not null, `logger.LogDebug("Conductor woken by {Event}.", reason);`.
- Nothing else in the worker changes. In particular the first pass at start still runs unconditionally, and
  the `finally` that stops sessions stays.
- Update the class summary to say it also runs a pass whenever a task crosses a handoff (`ConductorWake`).

### Registration (`Startup.cs`)

- `builder.Services.AddSingleton<ConductorWake>();` next to `AddSingleton<ConductorService>()`. Always, not
  inside the `BackgroundServices` block: tests resolve it, and the subscription is inert without a waiter.

### `sim run` (`SimCommands.cs`)

- Set `Muthur__ConductorIntervalSeconds` to `"15"` (the floor; `5` was silently raised to it anyway).
- Change the stderr line to: `the conductor wakes on each handoff and otherwise looks every 15s. Ctrl+C stops the run.`
- Nothing else in the sim changes. The report already measures the four phases.

## Units of work

### Unit A — wake-up
- **Files:** created `src/Muthur.Server/Services/ConductorWake.cs`; modified
  `src/Muthur.Server/Services/ConductorService.cs` (the `ConductorWorker` class only),
  `src/Muthur.Server/Infrastructure/Startup.cs`, `src/Muthur.Cli/Commands/SimCommands.cs`; created
  `tests/Muthur.Server.Tests/ConductorWakeTests.cs`.
- **Does:** everything under Design.
- **Depends on:** nothing.
- **Acceptance:** the tests below, written in `ConductorWakeTests.cs` using `HubFactory` with
  `Muthur:ConductorEnabled = true` and `Muthur:ConductorSessionsPerTaskDay = 0`, all pass; the whole suite
  passes; `dotnet build` has zero warnings.
  1. **A handoff wakes a parked wait without the clock moving.** Resolve `ConductorWake` from
     `_hub.Services`; start `var wait = wake.WaitAsync(TimeSpan.FromSeconds(60), ct)`; over HTTP register an
     agent, add a task, claim it. `await Eventually.CompletesAsync(wait, …)` returns `"task.claimed"`.
     Assert `_hub.Clock` was never advanced (the test does not advance it) and the wait completed anyway.
  2. **Each of the four handoffs wakes.** Drive one task through claim → spec → implemented (with
     `TestRepo`, as `ConductorTests.OwnedTaskInValidationAsync` does, on a project with no validators so that
     `task.implemented` and `task.validated` are recorded in one mutation) and assert a wait parked before the
     `implemented` call completes with `"task.implemented"` (the first matching type in the batch). Then for
     `task.validated` on its own: a project with one validator role, a validator agent passing the verdict
     over HTTP, a wait parked before the `pass` call completes with `"task.validated"`. For
     `integration.passed`: reuse the shortest existing path that records it (see how
     `tests/Muthur.Server.Tests/ConductorTests.cs` or `IntegrationTests` drive `Routes.IntegrationVerdict`);
     the wait parked before the verdict completes with `"integration.passed"`.
  3. **Other events do not wake it.** Park a wait; add a task over HTTP (`task.added`) and send a heartbeat;
     assert `wait.IsCompleted` is false and `wake.Pending` is false; then `_hub.Clock.Advance(60 s)` and the
     wait completes with null.
  4. **Nudges coalesce and are never lost.** With no wait parked, publish two transition batches on
     `EventFeed` directly (`feed.Publish([new LedgerEvent { Type = "task.claimed", … }])` twice); `Pending`
     is true; `WaitAsync` returns `"task.claimed"` immediately; a second `WaitAsync` does not complete until
     the clock is advanced by the fallback, then returns null.
  5. **The worker staffs on the wake, not the tick.** Build the worker with
     `ActivatorUtilities.CreateInstance<ConductorWorker>(_hub.Services)` and `StartAsync`. Set
     `_hub.Validators` to record starts. Define a validator role and a project requiring it, then push a task
     to `implemented` over HTTP (the transition). Without advancing the clock,
     `await Eventually.TrueAsync(() => _hub.Validators.Started.Count == 1, …)`. Then `StopAsync` the worker
     and assert `_hub.Clock.Timers` contains no entry shorter than the interval other than those the hub
     creates for the long-poll (compare against a snapshot taken before the transition: the worker must not
     have created a new interval timer between the transition and the staffing).
     If (5) proves flaky for reasons in the hub rather than in this change, replace the timer assertion
     with the count assertion alone and say so in the report.
