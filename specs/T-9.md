# T-9 — Outbound gate: allowlisted targets, secret scan, peer review of the exact bytes, founder approval, delivery

> Specialist-tier task: designed and built by the orchestrator tier directly. Design: `docs/PLAN.md` (M8).

## Design (as built)

Nothing leaves the machine except through `muthur out`, and the hub — not the agent — transmits.

1. **Allowlist.** `muthur out target <key> --channel file|discord-webhook|github-issue --address … [--founder-approval] --founder`.
   Only the founder defines targets. Addresses are never returned by the API (a webhook URL is a credential).
2. **Draft.** `muthur out draft --target <key> --file <f>`: unknown target → `target_not_allowed`; text containing a
   credential → `secret_detected`, and the text is **not stored**. Channel limits (e.g. Discord's 2000 chars) are checked here.
   The body is immutable from this point; its sha256 is recorded.
3. **Peer review.** `muthur out show O-n` then `muthur out review O-n --approve|--reject --sha <sha256> [--note]`:
   reviewer ≠ author (`self_review`), the sha must be the body's (`sha_mismatch`), a rejection needs a note, and with
   `Muthur:RequireCrossProviderReview=true` the reviewer must run on a different provider (`same_provider`).
   If the role `outbound-reviewer` exists, the hub messages it when a draft is waiting.
4. **Founder approval** for targets that demand it: `muthur out approve|decline O-n --founder` (status `awaiting_founder` until then).
5. **Send.** `muthur out send O-n` (author or founder): re-checks status, founder approval, that sha256(body) still equals
   the reviewed hash (`body_changed`), re-scans for secrets, then delivers. Failure → status `failed`, exit 3, `muthur out retry O-n`.

Every step is a ledger event carrying the sha256.

## Verification

```
dotnet build && dotnet test     # SecretScannerTests, OutboundGateTests, OutboundTests, CrossProviderOutboundTests
```

Against a scratch instance with agents `a1` (author) and `a2` (reviewer), using a `file` target pointing into the scratch directory:
- `out draft --target nope …` → exit 2 `target_not_allowed`. `out target …` without `--founder` → exit 6.
- A draft containing `ghp_` + 36 chars, an AWS key, a `Password=…;` connection string, or a Discord webhook URL → exit 2
  `secret_detected`; the message names the kind but never prints the secret; `out list --status all` does not contain it.
- Happy path: draft → `out show` → review with the right `--sha` by `a2` → `out send` by `a1` → the outbox file contains the body exactly.
- `a1` reviewing its own draft → exit 2 `self_review`; review with a wrong `--sha` → exit 2 `sha_mismatch`; send before review → exit 2 `not_approved`;
  send by `a2` → exit 2 `not_author`; sending twice → exit 2.
- Founder target: after peer approval status is `awaiting_founder`, send → exit 2; `out approve --founder` → send works; the author's inbox has the founder's message.
- `task show`/`log` show `outbound.drafted|approved|sent` with the same sha256.
- A `github-issue` target with a malformed address is refused at `out target` time… no: at draft time (`invalid_address`); a `discord-webhook` body over 2000 chars → `body_too_long`.
