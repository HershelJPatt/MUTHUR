# T-9 — Outbound gate: allowlisted targets, secret scan, peer review of the exact bytes, founder approval, delivery

> Specialist-tier task: designed and built by the orchestrator tier directly. Design: `docs/PLAN.md` (M8).

## Design (as built)

Nothing leaves the machine except through `muthur out`, and the hub — not the agent — transmits.

1. **Allowlist.** `muthur out target <key> --channel file|discord-webhook|github-issue --address … [--founder-approval] --founder`.
   Only the founder defines targets. Addresses are never returned by the API (a webhook URL is a credential).
2. **Draft.** `muthur out draft --target <key> --file <f>`: unknown target → `target_not_allowed`; text containing a
   credential → `secret_detected`, and the text is **not stored**. Channel limits (e.g. Discord's 2000 chars) are checked here.
   The body is immutable from this point; its sha256 is recorded.
3. **Peer review.** `muthur out show O-n` then `muthur out review O-n --approve|--reject --sha <sha256> [--note]`:
   reviewer ≠ author (`self_review`), the sha must be the body's (`sha_mismatch`), a rejection needs a note, and with
   `Muthur:RequireCrossProviderReview=true` the reviewer must run on a different provider (`same_provider`).
   If the role `outbound-reviewer` exists, the hub messages it when a draft is waiting.
4. **Founder approval** for targets that demand it: `muthur out approve|decline O-n --founder` (status `awaiting_founder` until then).
5. **Send.** `muthur out send O-n` (author or founder): re-checks status, founder approval, that sha256(body) still equals
   the reviewed hash (`body_changed`), re-scans for secrets, then delivers. Failure → status `failed`, exit 3, `muthur out retry O-n`.

Every step is a ledger event carrying the sha256.

## Verification

```
dotnet build && dotnet test     # SecretScannerTests, OutboundGateTests, OutboundTests, CrossProviderOutboundTests
```

Against a scratch instance with agents `a1` (author) and `a2` (reviewer), using a `file` target pointing into the scratch directory:
- `out draft --target nope …` → exit 2 `target_not_allowed`. `out target …` without `--founder` → exit 6.
- A draft containing `ghp_` + 36 chars, an AWS key, a `Password=…;` connection string, or a Discord webhook URL → exit 2
  `secret_detected`; the message names the kind but never prints the secret; `out list --status all` does not contain it.
- Happy path: draft → `out show` → review with the right `--sha` by `a2` → `out send` by `a1` → the outbox file contains the body exactly.
- `a1` reviewing its own draft → exit 2 `self_review`; review with a wrong `--sha` → exit 2 `sha_mismatch`; send before review → exit 2 `not_approved`;
  send by `a2` → exit 2 `not_author`; sending twice → exit 2.
- Founder target: after peer approval status is `awaiting_founder`, send → exit 2; `out approve --founder` → send works; the author's inbox has the founder's message.
- `task show`/`log` show `outbound.drafted|approved|sent` with the same sha256.
- A `github-issue` target with a malformed address, or a relative path for a `file` target, is refused when the target is defined (`invalid_address`); a `discord-webhook` body over 2000 chars is refused at draft (`body_too_long`).

## Round 2 (after win-1's failed validation)

1. **Scanner bypasses that were delivered** — now caught: JSON/YAML-quoted keys (`"password": "…"`, `"api_key":"…"`), any `*secret*`/`*access_key*`/`*private_key*`
   assignment (`aws_secret_access_key = …`), `token: <16+ opaque chars>`, credentials in URLs of any scheme (`postgres://u:p@h`, `mongodb+srv://`,
   `redis://:p@h`, `https://u:p@h`), more vendor prefixes (`sk_live_`, `rk_live_`, `npm_`, `glpat-`, `pypi-`, `dop_v1_`, `shpat_`, `hf_`), and
   tokens split by a newline, a space, markup tags or zero-width characters (token shapes are also matched on a copy of the text with
   invisible characters, tags and whitespace removed). Every reported bypass is a unit test (`Shapes_that_once_slipped_through_are_found`,
   `A_token_split_by…`). **Known and accepted limit:** a pattern matcher cannot catch arbitrarily encoded secrets (base64, reversed, spelled out);
   that is what the second reader is for. Try new shapes — report any realistic credential format that passes.
2. **Any delivery exception** (not only IO/HTTP ones) → status `failed`, exit 3 `delivery_failed`, retryable. Repro: a `file` target whose path is a directory.
3. **The target address no longer leaks on failure**: it is redacted from the error in the response, `out show`, the ledger payload and therefore the Operations page.
4. `out retry` checks authorship before changing anything (`not_author` leaves the message `failed`, no `outbound.retrying` event).
5. `outbound.founder_approved|declined` carry the sha256; the `file` channel writes the body byte for byte (no trimming).

## Round 3 (after win-1's second failed validation)

**What changed in approach.** Two rounds showed that chasing individual shapes does not converge, so the scanner's contract is now a
corpus: `tests/Muthur.Core.Tests/SecretCorpus/block.txt` (must all be refused) and `pass.txt` (must all pass). Every shape reported in
rounds 1 and 2 is a line in `block.txt` (tokens are split with `~`, which the test removes, so the file itself never contains a literal
credential). A shape found later is fixed by adding a line there first. `dotnet test` runs the corpus.

1. **Scanner.** Key names now match when they *contain* a sensitive word (`SECRET_KEY_BASE`, `aws_secret_access_key_prod`, `smtpPassword`,
   `DB_PASS`, `PASS`, `pw`, `Passwort`, `passphrase`), with `= : := =>`, a tab or a full-width colon as separator, a YAML block scalar, and a
   6-character floor for password-named keys; weak vocabulary (`token`, `*_key`, `credentials`, `_auth`) needs a 16+ character opaque value;
   prose (`the password is …`, netrc `password <value>`, value must contain a digit); XML element and `key="…Password" value="…"` forms;
   `Authorization: Basic|Bearer|Token`, `curl -u/--user user:pass`, `mysql -p…`, docker/npm `auth`; URL credentials of any scheme; more vendor
   shapes (SendGrid, Google `ya29.`/`GOCSPX-`, Slack `xapp-`, Vault `hvs.`, Stripe `whsec_`, Twilio, Telegram, Discord bot, Mailgun, Linear,
   Square, New Relic, age); key material without a PEM header (OpenSSH body, PuTTY); htpasswd/shadow hashes; Teams and Telegram bot URLs;
   a long opaque value on any line that mentions key/secret/token/password/credential/auth; and the joined copy now also drops markdown
   emphasis, backticks, line-continuation backslashes, quotes and `+` (string concatenation).
   Placeholders are not credentials: values starting with `$`, `<`, `{{`, `%`, `***`, `xxx`, `your`, `example`, `changeme`, `redacted`
   (fixes the `export API_KEY=$YOUR_KEY` false positive).
2. **No address leak, by construction.** Channel failures are never reported with the exception's text. Channels throw `ChannelException`
   with a fixed, safe reason; anything else is mapped by exception type to a fixed text ("access to the target was denied", "the target
   path is unavailable", "the target answered HTTP 404", "the target timed out"…). The detail goes to the hub log only. Test:
   `A_failure_whose_os_message_names_part_of_the_address_reveals_nothing` is the validator's exact reproduction.
3. The failure message no longer has a double full stop.

**How to judge this round.** Re-run every string from rounds 1 and 2 (all must be refused at `out draft`) and the parent-path leak
reproduction (the path, its parent and the file name must appear nowhere an agent can read; the hub log may contain it). Then attack
again. A delivered credential in a mainstream plaintext format is still a fail. The accepted limits are: encodings and ciphers (base64 of
a whole secret, reversed, spelled out, split across separate messages), and a bare high-entropy string with no keyword, prefix or structure
around it (indistinguishable from a commit id or a hash) — report those as observations with a suggested corpus line, not as a fail.
Check `pass.txt`-style ordinary texts too: the gate must stay usable.

## Round 4 (after win-1's third failed validation) — a change of design, not more patterns

Round 3 showed the real problem: one verdict cannot be both safe and usable. Broad rules refused one ordinary text in five;
narrow rules let `docker login -p …`, table cells and name/value pairs through. So the scanner now gives **two verdicts**:

- **Block** — a recognizable credential (vendor token shapes, key material, URL credentials, auth headers, connection strings, a
  password-named assignment whose value has a digit or symbol, …). `out draft` refuses it (`secret_detected`) and nothing is stored. As before.
- **Suspect (flag)** — text that *might* hold a credential: a standalone mixed-class token (8+ chars, with a digit or symbol, not a URL,
  path, hash, id, version, number, e-mail, identifier or placeholder) on a line that mentions a password-class word (password, pw, secret,
  credentials, login, token, api key, `-p`/`-P`/`-a`, `--password`, `IDENTIFIED BY`, `SecureString`, `NetworkCredential`, `auth=`, `/user:`) **or
  within two lines below one** (tables, YAML/JSON name–value pairs); plus password-named assignments whose value has no digit or symbol, and long
  opaque values near key words. A flagged draft is stored with its masked `flags`, and **whatever its target, it can only leave with the
  founder's approval**: after peer approval it becomes `awaiting_founder`; `out send` refuses until `out approve --founder`. A peer reviewer
  cannot wave a flagged message through. A false positive therefore costs the founder one look, not the agents a useless gate.
- Placeholders must be the whole value and read like one (`$TOKEN`, `${DB_PASSWORD}`, `$password`, `<your key>` without digits,
  `{{ … }}`, `%VAR%`, `****`); `$up3rS3cret9` and `<Sup3rS3cret9>` are not placeholders. Code references (`settings.DB_PASSWORD`,
  `TimeSpan.FromMinutes(30)`) and one short lowercase word (`keyvault`) after a password-like name are configuration.
- More vendor prefixes are blocked (Docker, Atlassian, Databricks, GitLab runner, Grafana, Postman, Terraform, Doppler, Notion, Figma,
  Pulumi, PlanetScale, Mapbox, `*_PAT=`).

The corpus now has four files, all run by `dotnet test`: `block.txt` (must be blocked), `flag.txt` (must at least be flagged — every
mainstream shape delivered in round 3 is here), `pass.txt` (must not be blocked), `clean.txt` (everyday messages: **no finding at all**,
including every false positive reported in round 3).

**How to judge this round.**
1. Rounds 1–3 strings: each must be blocked, or flagged such that it cannot be sent without `out approve --founder`. Verify the flag path for
   real: draft a flagged text, approve it as the peer, confirm `awaiting_founder` and that `out send` exits 2; then approve as founder and send.
2. A **fail** is a mainstream plaintext credential that reaches the outbox with **no founder approval** (neither blocked nor flagged).
   The accepted limits stay: encodings/ciphers, a bare high-entropy string with no keyword, prefix or structure near it, a secret split
   across separate messages — and now also a password made only of letters with no password-class word within two lines.
3. Usability is measured on *no finding at all*: of ordinary texts, how many are blocked (should be ~0) and how many are flagged
   (a flag is acceptable for texts that really do contain a token-like string next to a password word; more than ~1 in 6 flagged is a fail).
4. Regression of the review/approval/send rules and the two address-leak reproductions (unchanged since round 3).

## Round 5 (after win-1's fourth failed validation)

The two-verdict design held; the defect was which texts got a flag. Fixed, with every reported string now in the corpus **verbatim**
(non-vendor values, so the surrounding shape is what is tested):

- Password-class words no longer use word boundaries: `GITHUB_TOKEN`, `API_TOKEN`, `DB_PWD`, `AccessToken`, `DEPLOY_TOKEN` count, so
  name/value pairs in separate fields or lines, table rows, `setx API_TOKEN …`, `--name DEPLOY_TOKEN --value …` are flagged.
- A password flag with its value glued on (`-pSECRET`, `-wSECRET`, `/p:SECRET`) is flagged for any command; `-w`, `/p:` and `auth` are
  password-class words (`ldapsearch -w …`, `xfreerdp /p:…`, "Basic auth … is admin and …").
- Letters-only prose (`the password is CorrectHorseBatteryStaple`), quoted passphrases with spaces (`password: 'My dog Rex 2019'`), short
  mixed tokens right next to a password word (`password = Sup3r S3cret`) and hyphenated passphrases are flagged.
- Notion's `ntn_` prefix is blocked.
- False positives fixed: a Key Vault reference (`@Microsoft.KeyVault(VaultName=…;SecretName=…)`) is a code reference, not a secret; names made
  of words and numbers (`ACME_PASSWORD_MIN_LENGTH=12`, `20240917_AddPasswordHashColumn`) and UUIDs are not opaque values; a letters-only
  word of up to 12 characters, or any all-lowercase word, after a password-like name is configuration (`KeyVault`, `incorrect`);
  trailing `)`/`.`/`,` no longer defeats these checks. All eight reported texts are in `clean.txt` verbatim.
- A Suspect flag now shows the (masked) value that raised it, not the start of the line.

Judging rule unchanged from Round 4. Known remaining limits, stated plainly: other languages' words for "password" beyond German and
French, a letters-only lowercase password, a vendor token with an unknown prefix and no keyword near it, and the accepted limits listed before.

## Round 6 (after win-1's fifth failed validation)

One defect: `.env`-style `NAME=value` where the name is a `*_KEY` the scanner had no word for (`MEILI_MASTER_KEY`, `FERNET_KEY`, `SESSION_KEY`,
`APP_KEY=base64:…`, `KEY=`, `HMAC_KEY`, `CONSUMER_KEY`, `STORAGE_KEY`, `JWT_KEY`) passed clean, while the colon, JSON and spaced spellings were flagged.
Fixed: any identifier containing `key` as a word part (`KEY`, `_KEY`, `fooKey`, `key`) followed by an assignment and a 16+ character value is a
weak credential assignment (blocked when the value has a digit or symbol and is not an identifier, reference or placeholder); `key` in those
forms is a password-class word for the context rule (not `keyboard`, `monkey`); `<add key="…Key" value="…"/>` is covered; and a value standing alone under
a line that is nothing but a sensitive name (`api_token:` ⏎ `<40 hex>`, `SUPABASE_ACCESS_TOKEN` ⏎ `sbp_…`) is flagged even when it looks like a hash.
All reported strings are in `flag.txt` verbatim; four everyday "key" sentences are in `clean.txt`. Judging rule unchanged (Round 4).

## Round 7 (after win-1's sixth failed validation — security held, usability did not)

Round 6's `key` rule blocked everyday text (S3 object keys, Terraform backend `key =`, `Idempotency-Key:`, cache keys, key file paths, `key_name`).
Fixed by one principle: **for the weak vocabulary (`key`, `token`, `credentials`, `_auth`, `_pat`) only an opaque value counts.** A value is
excused when it has word structure — a file name, a UUID, or words and numbers joined by separators (`reports/2026/q3/summary.pdf`,
`orders:by-customer:v3`, `deploy-keypair-2026`, `createdAt#orderId`, `order-2026-09-17-000123`) — when it is letters only, or when the
assignment's name says it is a location, label or number (`…_PATH`, `…_FILE`, `key_name`, `KeyPath`, `KEY_SIZE`, `…_ROTATION_DAYS`, `…_ID`, `…_URL`).
After an explicit assignment a hex or base64 run is still the value, so `ENCRYPTION_KEY=<32 hex>`, `_auth=<base64>`, `FERNET_KEY=…=` stay blocked.
The context rule uses the same structure test, requires a digit (or a symbol inside a mixed-case word), and no longer reads keyboard chords,
`0x…` key ids, SSH fingerprints and public keys, `user@host`, `~/…` paths, `${{ … }}` expressions or `!code.Calls` as candidates; "passed"/"passing"
are no longer password words. The XML attribute `key="LongSettingName"` is a letters-only value and is ignored.
A blocked excerpt now shows the name and masks the whole value (`KEY=****** (40 chars)`), never its first characters.

All 25 texts reported in round 6 are in `clean.txt` verbatim (no finding at all). Rounds 1–6 credential strings are unchanged in `block.txt`/`flag.txt`
and still caught. Judging rule unchanged (Round 4). Follow-ups noted, not done: `*_SEED` names as Suspect.

## Round 8 (after win-1's seventh failed validation — usability held at 0 blocked / 3.4 % flagged; the round-7 relaxation excused too much)

- **Family A.** Word structure now excuses a value only under a bare `key` name. Under a credential-grade name (`*token*`, `api_key`, `access_key`,
  `private_key`, `*secret*`, `credentials`, `auth…`, `_pat`, `license`) a structured or UUID value that contains a digit is a **Suspect flag**
  (some services' tokens really are UUIDs; `staging-admin-2026` is a password). In prose and name/value pairs, a UUID within ~45 characters
  after such a word, or under a line that carries one, is flagged too — unless the name right before it says it is an id (`tenantId: <uuid>`).
  `Idempotency-Key: <uuid>`, correlation ids and request ids stay clean.
- **Family B.** "Structured" now means *every* segment is a word, a number, or a word with a number on it (`x64`, `v3`, `build01`). One opaque
  segment makes the value a token wearing a prefix or dashes: `gsk_…`, `phx_…`, `acme_Sup3rS3cretValue9`, `prod-…`, `aZ3k-Q9mX-2vB7-…` are no
  longer excused anywhere (assignments, the context rule, tables, name/value pairs, CLI flags).
- A name that says the value is a label, location or number (`secretName:`, `…_FILE`, `passwordMinLength`) now excuses strong assignments as well.
- All 37 strings reported in round 7 are in `flag.txt` verbatim (prefixes kept); 15 more everyday token/secret/password/credentials texts are in `clean.txt`.

Judging rule unchanged (Round 4). Follow-ups noted, not done: trailing `?` on identifiers, `Argon2id` near "password", `*_SEED` names.

## Round 9 (after win-1's eighth failed validation — rounds 1–7 closed, usability 6.7 % flagged / 1 blocked; one old hole)

The hole: the "identifier" and "code reference" excuses applied to values everywhere, so the most common human password shapes —
`Winter_2026`, `Welcome.2026`, `Acme.Prod.2026`, `John.Smith1984` — and `stg.`-prefixed tokens passed clean in every carrier.

- In a **credential position** a value that contains a digit is excused only if it is a placeholder, a URL/path, or visibly a call
  (`TimeSpan.FromMinutes(30)`); being made of words and numbers no longer excuses it. Credential positions are: every context pattern's value
  (after a password-grade name, connection strings, URL userinfo, `-u user:`, XML forms, prose `password is …`) and, for the context rule, the
  token right after a password flag (`-p X`, `-P X`, `-w X`, `--password X`, glued `-pX`, a `net use … /user:` line), right after the password
  word with only separators between (`password: X`, `**Password:** X`, `Password - X`), in a table/CSV row under a header that names a password,
  under a line that is only a secret name, or on a `value:` line under a line naming a password.
- A line that merely *mentions* passwords is not a credential position: `Password reset was delayed on smtp02; fixed in release-2026.09`,
  `PBKDF2 … HMAC-SHA256`, `PasswordPolicyV2 … build01-win-x64 … Chrome128` stay clean (all in `clean.txt`).
- A value with an opaque segment (12+ mixed letters and digits) is never a code reference or identifier (`stg.Qw7Lp2Rm9Xt4Zk8Nb6Ja`).
- A token that itself carries the password word is a name, never the value (`20240917_AddPasswordHashColumn`, `DB_PASSWORD`).
- `arn:…:secretsmanager:…:secret:…` is a resource name, not an assignment (was the one blocked ordinary text). `adminPass` (camelCase) is a password word.
- All 20 round-8 strings are in `flag.txt` verbatim; 7 more everyday texts in `clean.txt`.

Judging rule unchanged (Round 4). Follow-ups noted, not done: a UUID two lines under a `Token` table header; `codecov -t <uuid>`;
`accessTokenCache?`; `Argon2id`; `1Password`; `*_SEED`; `PRODUCT_LICENSE=`.

## Round 10 (after win-1's ninth failed validation — steps 2, 3 and 4 passed; the round-8 hole was narrowed, not closed)

Round 9 recognised a credential position only when the value was glued to the password word or flag. The validator's point: the scanner
knew the carrier (it flagged the same texts with `Sup3rS3cretValue9`) and excused the value for its shape. Now:

- On any line that is **about** a password, a login or credentials (password/passwd/pwd/pw/pass, login, creds, credentials, `IDENTIFIED BY`,
  `SecureString`, `PSCredential`, `NetworkCredential`, a `-p/-P/-w/-a` flag), a token **shaped like a human password** is in a credential
  position wherever it stands on the line: it has a digit and a letter and either a capitalized word (`Welcome_2026`, `AppUser2026`,
  `Orders.Db.2026`, `Build_2026`) or a symbol (`P@ssw0rd`, `Spring@2026`). That covers "Temporary password for the new hire: …", "The password
  for the staging admin is …", "root pw on build01 changed to …", `IDENTIFIED BY '…'`, `ConvertTo-SecureString '…'`, `login admin / …`,
  `Grafana login: admin:…`, `admin/… is the login`, one-line JSON name/value, and table rows.
- Infrastructure is not password-shaped: lowercase names (`smtp02`, `release-2026.09`, `build01-win-x64`), codes and standards (`AADSTS50126`,
  `KB5031356`, `SP800-63B`, `HMAC-SHA256`, `28P01`, `64MB`), branch-like paths (`task/T-9-outbound-gate`), and products, platforms and algorithms
  with a version (`Chrome128`, `Server2019`, `Windows11`, `Postgres16`, `Argon2id`) — the last two groups are now skipped by the context rule
  everywhere, which also clears the `Argon2id` / `AADSTS…` / `KB…` / `SP800-63B` flags reported in rounds 8–9.
- `-a X` is a password flag; a tab is a table delimiter; in a credential position `x@y` is an e-mail only if `y` is a real domain.
- **All 31 strings named in the round-9 evidence** (12 delivered, 19 clean at draft) are in `flag.txt` verbatim; the 5 flagged ordinary texts of
  that kind are in `clean.txt`.

Known cost, stated plainly: on a line about passwords or logins, a capitalized name with a number that is not a known product
(`Pixel8`, `Sprint42`) gets a flag. Judging rule unchanged (Round 4). Follow-ups unchanged from Round 9, plus `--password-stdin` pipes and `htpasswd -b`.

## Round 11 — what changed after the tenth failed validation

Round 10 closed round 9's hole, held every earlier string (0 weaker of 839), and passed usability (0 blocked; 14.4 % flagged even with 60
adversarial texts) and the flag path. It failed on one carrier: a table or CSV whose credential column is headed `Secret`, `Credentials`,
`Token` or `API Key` rather than `Password`.

- A table/CSV header now names a credential column with any of password/pwd/pw/passphrase/passcode/passwort, **secret, credential(s), creds,
  token, api key**. A bare `key` is deliberately left out (`key,value` heads far more tables than secrets do).
- `-storepass` / `-keypass`, `net user <name> <value>` and `sqlplus user/pass@db` now make a line a credential line.
- The validator's four strings, plus an `API Key` and a tab-separated `creds` variant and the three commands above, are in `flag.txt` verbatim;
  three ordinary tables (`| Secret | Rotation | Owner |`, `| Token type | Lifetime |`, `key,value`) are in `clean.txt`.

Still accepted limits (Round 4): no password/login/credential word anywhere near the value (`db2 … using Winter_2026`,
`use admin / Welcome_2026 to get in`). Judging rule unchanged.
