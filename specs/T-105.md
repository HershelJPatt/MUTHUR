## Design
### Durable candidate and API
Add IntegrationCandidate entity/table with GUID Id, ProjectId, TaskId, SubjectId, canonical RepositoryPath, DefaultBranch, TargetSha, ImplementationSha, nullable CandidateSha/TreeSha, RequiredChecksJson, State, AssignedAgentId, LeaseExpires, Attempt, CreatedAt/StartedAt/CompletedAt, nullable EvidenceJson/EvidenceSha256, FailureCode/FailureMessage. State wire values: assigned, checking, passed, failed, invalidated, interrupted, promoted. Retain all historical rows; new attempt has a new identity. Add nullable WorkTask.CurrentIntegrationCandidateId and mapping. Register all DTOs in source-generated JSON. One globally active assigned/checking candidate; passed candidate occupies the slot until promoted or invalidated. This first slice processes one project/task at a time and contains exactly one independently approved subject per candidate. FIFO by first validated event seq, task ID tie-break; retries go behind already waiting tasks. No priority-based starvation.

Add IntegrationService for ledger-only lifecycle and verification reads through ITaskLander git inspection helpers. Routes under /api/tasks/{id}/integration: GET latest/history; POST claim; POST candidate; POST verdict. CLI: muthur integration show T-n; muthur integration run T-n. Claim returns immutable assignment and random assignment GUID; caller must be identified, not task owner, and be a registered mastermind validator or founder. Conductor-assigned deterministic runner uses an ordinary registered conductor identity with no founder token; explicitly allow that identity only for its assigned task and candidate. The runner has no task owner, implementation, land or outbound authority. Reject arbitrary agent spoofing using persisted assigned agent ID and authenticated caller, not name matching. Existing validator independence rules still gate task approval. Read/status available to existing task readers.

Claim requires task validated, all current subject verdicts/evidence passing, Validations.RequireCurrentAsync, current task branch equals ImplementationSha, eligible FIFO task and free global slot. Snapshot target SHA from actual default branch and check policy from approved subject. Empty/missing build and test commands is integration_checks_missing, not a passing no-op. Required checks are reviewed subject build/test commands; candidate content may alter config but cannot substitute unreviewed commands. Revalidate/resubmit/spec/policy/branch drift invalidates the candidate; main movement invalidates integration only, preserving compatible per-task verdicts. Recheck all identifiers on candidate registration, verdict and promotion. Use stable 409 stale_integration_candidate/ integration_target_changed for stale identity/target and 422 integration_required when no current passed integration candidate exists, and 422 integration_checks_missing when the approved subject lacks a required build or test command. Persist invalidations before returning errors, as in CheckSubjectAsync.

POST candidate supplies assignment ID, candidate commit/tree, exact target/implementation; hub verifies the commit exists in repository, tree matches, and ordered parents are target then implementation (if implementation is already ancestor of target, candidate may equal target with explicit alreadyIncluded=true; still test it). Never trust only submitted SHA text. Candidate registration is immutable and idempotent for identical payload, conflict otherwise. Add POST failure on the same integration route for pre-check failures. Payload: assignmentId, subjectId, phase (construction|checkout|launch), code (merge_conflict|checkout_failed|shell_unsupported|runner_cancelled|runner_timeout|runner_failed), message (nonempty), optional artifact reference/digest, and files/landedSince arrays for conflicts. No candidate SHA, checkout SHA or check outcomes are required or inferred on this route. Only the persisted assigned caller with matching live lease/subject may report; assigned/checking states only, never passed/promoted. Record an actionable failed state, return task to owner in_progress, retain independent verdict history, release global slot atomically, and record integration.failed. A repeated identical failure is idempotent; a different terminal payload conflicts. Lease expiry instead records interrupted and follows bounded retry policy; late failure payloads cannot close a newer assignment. This endpoint can never pass or promote a candidate. POST verdict is exclusively for registered candidates and completed check reports; it requires assigned caller, assignment/candidate/subject IDs and structured report: build/test commands, exit codes, durations, artifact references and SHA-256 digests of local output, started/ended time, actual checkout SHA. All required checks must pass for passed. Hash canonical report UTF-8 in hub as evidence identity. This records runner evidence, not cryptographic proof against a malicious trusted runner. Reject missing checks, wrong commands/SHA or expired/superseded lease. Identical repeated report is idempotent; differing second report conflicts. Never read arbitrary report paths/URLs on server. Failure returns task to owner in_progress with actionable command/exit/artifact and invalidation reason, retaining subject, verdicts and history; owner follows existing revalidate/resubmit path. Include git conflict files and T-16 landedSince hints. Unrelated queued tasks remain eligible.

### Promotion and crash recovery
LifecycleService.LandAsync retains independent subject/state/owner gates, and requires current passed integration candidate for merge mode; no opt-out flag. Recheck subject compatibility, branch SHA, candidate structure, evidence completeness and current default SHA under landing semaphore/ledger write. GitLander promotes exact CandidateSha only; never creates another merge commit. For default branch not checked out, update-ref with expected TargetSha is mandatory. For a default branch checked out in any worktree, refuse promotion with integration_target_checked_out before changing any ref or checkout. Recovery message names the checkout and asks its owner to switch that checkout to a non-default branch or detached HEAD using ordinary authorized workflow, then retry. Never automatically switch, reset, stash, or synchronize a user checkout. This explicit first-slice limitation avoids the non-CAS race in git merge --ff-only when an external writer advances target to another ancestor of the candidate. Recheck checkout inventory immediately before compare-and-swap; concurrent external checkout creation is an unsupported concurrent repository mutation and must be documented. Atomic target compare-and-swap remains mandatory for every supported promotion. Existing dirty-checkout refusal remains actionable, but no checked-out promotion is attempted. Main movement before promotion invalidates candidate and queues new one, without changing main. Persist promotion intent (candidate identity) before git side effect, then finalize ledger result; do not rely on a transaction rolled back by process crash to retain intent. Recheck gates inside final serialized promotion region after intent commit. On restart after git promotion before ledger finalize, verify recorded candidate exists and is exactly current main or ancestor of current main with recorded target parents and passed evidence, then finalize exactly that candidate once. Merely observing implementation ancestor is never sufficient. Repeated land on done task with matching promoted record is idempotent; do not duplicate events. Candidate-ref creation before registration is recovered from assignment ref after interruption; preserve evidence, never infer pass. Add deterministic crash barriers/fakes for each boundary.

PR mode retains existing pinned approved ref, independent gate and human merge responsibility. Add explicit PR body/ledger metadata integration status delegated_external_checks_unknown: local hub does not certify remote integrated result. Document external CI must test exact base/head merge result and hosting checks must enforce freshness; unsupported/unavailable required merge checks are unknown/unsupported, never reported passed. No new gh/network operations or paid-plan assumptions.
