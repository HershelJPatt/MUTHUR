# T-22 — The server test suite is flaky under load

> Frozen spec. An implementer completes this without making design decisions.
> If something here is wrong or missing, the implementer stops and reports; they do not improvise.

## Goal

After this task, `tests/Muthur.Server.Tests` contains no test that uses elapsed wall-clock time as a
synchronization barrier, and no test that asserts on work a detached (fire-and-forget) task has not
been observed to finish. A validator who runs `dotnet test` on a loaded machine and sees red can trust
that the red is about the change under validation.

This matters because every validator treats `dotnet test` as ground truth. A suite that fails for
reasons unrelated to the change teaches validators to re-run until green, which is the habit that lets
a real regression through — and an unattended conductor-started validator cannot decide to re-run at all.

## Context

### What was reproduced, and how

The flake is real and now has a recipe. On a 24-core Windows box, twelve runs of the server suite at
six-way concurrency (six `dotnet test` processes at a time, two passes) produced one failure:

```
[xUnit.net 00:00:25.81]     Muthur.Server.Tests.MessagingTests.A_waiting_inbox_times_out_empty [FAIL]
Failed!  -  Failed: 1, Passed: 138, Skipped: 0, Total: 139
```

Eighteen runs at one- and three-way concurrency before that were all green, which is why this only shows
up when a machine is busy.

### The mechanism, exactly

`MessageService.InboxAsync` computes its deadline **when the request reaches the server**:

```csharp
var deadline = clock.GetUtcNow() + TimeSpan.FromSeconds(Math.Clamp(waitSeconds, 0, MaxWaitSeconds));
```

`MessagingTests.A_waiting_inbox_times_out_empty` starts the call, sleeps 150 ms of real time, and then
advances the fake clock once:

```csharp
var waiting = InboxAsync(waiter, wait: 60);
await Task.Delay(150);
_hub.Clock.Advance(TimeSpan.FromSeconds(61));
var inbox = await waiting.WaitAsync(TimeSpan.FromSeconds(10));
```

On a loaded machine 150 ms is not enough for the request to reach `InboxAsync`. The clock then moves
*before* the deadline is computed, so the deadline lands 61 s further out than the test believes, the
advance is consumed by nothing, and the poll waits for fake time that never comes. Ten real seconds
later `WaitAsync` throws and the test fails. There is no second advance, so the test can never recover.

`Task.Delay(150)` appears three more times in the same file with the same intent — "give the server a
moment" — and the real-time budgets on the `WaitAsync` calls (5 s and 10 s) are tight enough that a
loaded machine can exceed them on their own.

### The second shape: detached work asserted synchronously

`ConductorService.RunPassAsync` deliberately does not wait for the sessions it staffs:

```csharp
_ = RunSessionAsync(assignment, key);
```

`RunSessionAsync` calls the launcher, and on failure takes `lock (_launchFailures)` and updates the
failure count **before** its first `await`; so both `FakeValidatorSessions.Started` and the stall
bookkeeping are settled by the time `RunPassAsync` returns. That part is safe and must not be changed.

What is *not* settled is the ledger event: `conductor.failed`, `conductor.session_failed` and
`conductor.stalled` are written by `await ledger.MutateAsync(...)` inside that detached task, and so is
`_lastAction`. `ConductorTests` reads all of them immediately after the last pass returns. On an idle
machine the continuation almost always wins the race; under load it need not. This has not been observed
failing, and it is the same class of defect as the one that was.

### Investigated and cleared — do not re-tread

`HubFactory.Dispose` calls the process-global `SqliteConnection.ClearAllPools()`, which looked like a
plausible way for one finishing test class to disturb another still running (which is the shape of
`OutboundTests.Bytes_changed_after_review_are_not_sent` failing on unchanged `main`). It was tested
directly: eight threads running SQLite write transactions against a WAL database for twenty seconds
while another thread called `ClearAllPools()` every 2 ms produced 673 transactions and **zero**
failures. `ClearAllPools` does not disturb a connection that is in use. Leave `HubFactory.Dispose`
alone.

`OutboundTests.Bytes_changed_after_review_are_not_sent` did not reproduce in thirty runs and has no
timing construct in it; the `body_changed` rule it exercises is a pure function in
`src/Muthur.Core/OutboundGate.cs`. The most likely explanation is the general one this task fixes — a
loaded machine — expressed through some other real-time budget. If it recurs after this task, it needs
its own investigation with `--logger trx` captured, not a guess now.

## Non-goals

- **No production code changes.** `MessageService.InboxAsync` and `ConductorService.RunPassAsync` are
  correct as they stand: a pass that blocked on the sessions it starts would be a worse conductor. Do
  not add a test hook, a waiter gauge, a drain method, or an `internal` seam to either. Everything here
  is fixed in the test project.
- Do not change `HubFactory.Dispose` or its `ClearAllPools()` call (see above).
- Do not touch `IngestTests.cs:120` or `TaskLeaseTests.cs:43`. Those use `Task.WhenAll` over genuinely
  concurrent requests and assert that exactly one wins, which is the behaviour under test, not a barrier.
- Do not reduce what any test asserts in order to make it deterministic. Every assertion that exists
  today must still exist, or exist in a strictly stronger form.
- Not in scope: the other test projects (`Muthur.Core.Tests`, `Muthur.Launch.Tests`), which were grepped
  and contain no delay, sleep or wall-clock construct at all.

## Design

### The rule

A test may spend real time only as a **hang detector**: a budget generous enough that a loaded machine
never reaches it, whose expiry means the system has genuinely stopped making progress. A test may never
spend real time as a **barrier**: "sleep n milliseconds, by which point the server will have got there".

### New file: `tests/Muthur.Server.Tests/Eventually.cs`

```csharp
namespace Muthur.Server.Tests;

/// <summary>
/// Waiting without wall-clock guesses. Every budget here is a hang detector, not a pace: generous enough
/// that a loaded machine never trips it, so a test that does trip it has really stopped making progress.
/// </summary>
internal static class Eventually
{
    /// <summary>The real-time ceiling for anything a test waits on.</summary>
    public static readonly TimeSpan Budget = TimeSpan.FromSeconds(60);

    /// <summary>Returns once the condition holds, or fails naming what never became true.</summary>
    public static Task TrueAsync(Func<bool> condition, string because);

    /// <summary>Returns once the probe answers non-null, or fails naming what never arrived.</summary>
    public static Task<T> TrueAsync<T>(Func<Task<T?>> probe, string because) where T : class;

    /// <summary>Awaits a call that something else is expected to complete, within the budget.</summary>
    public static Task<T> CompletesAsync<T>(Task<T> call, string because);

    /// <summary>
    /// Awaits a call that ends when a server-side deadline passes, pushing the fake clock by
    /// <paramref name="step"/> until it does. The server computes that deadline when the request reaches
    /// it, which a test cannot observe, so the advance is repeated rather than done once.
    /// </summary>
    public static Task<T> AfterAdvancingAsync<T>(Task<T> call, FakeTimeProvider clock, TimeSpan step, string because);
}
```

Behaviour:

- Poll interval is 10 ms. The budget is measured with `DateTime.UtcNow` — this is the test harness's own
  stopwatch, not server or core code, so the injected-`TimeProvider` rule does not apply; no other
  `DateTime`/`DateTimeOffset` reading may be added to the test project.
- On expiry every method throws `Xunit.Sdk.XunitException` with the message
  `$"Waited {Budget.TotalSeconds:0}s and {because}"`. `because` is written to complete that sentence,
  e.g. `"the inbox never returned"`.
- `AfterAdvancingAsync` advances the clock once per poll and returns `await call` once `call.IsCompleted`.
  Advancing repeatedly is safe: the hub under test runs with `Muthur:BackgroundServices=false`, so
  nothing else is watching the clock.
- `CompletesAsync` wraps `call.WaitAsync(Budget)` and converts `TimeoutException` into the message above.
- Cancellation, configurable budgets and per-call overrides are deliberately absent. One budget, one
  poll interval.

### `MessagingTests` — exact changes

1. **`A_waiting_inbox_wakes_when_a_message_arrives`** — delete `await Task.Delay(150);`. Keep
   `Assert.False(waiting.IsCompleted, ...)`: the fake clock is frozen for the whole test and there is
   nothing to deliver, so the call provably cannot have completed at that point, with or without a
   delay. Replace `waiting.WaitAsync(TimeSpan.FromSeconds(10))` with
   `Eventually.CompletesAsync(waiting, "the inbox never woke for the message that was sent")`.

2. **`A_waiting_inbox_times_out_empty`** — delete `await Task.Delay(150);` and the single
   `_hub.Clock.Advance(...)`. Replace the await with:

   ```csharp
   var inbox = await Eventually.AfterAdvancingAsync(waiting, _hub.Clock, TimeSpan.FromSeconds(61),
       "the inbox never timed out, however far the clock was pushed");
   ```

3. **`Asking_a_founder_blocks_the_task_...`** (line 116) — replace
   `waiting.WaitAsync(TimeSpan.FromSeconds(10))` with
   `Eventually.CompletesAsync(waiting, "the asker was never woken by the founder's answer")`.

4. **`A_waiting_inbox_ends_the_moment_the_hub_stops`** — delete `await Task.Delay(150);`. Keep
   `Assert.False(waiting.IsCompleted);` for the same reason as (1). Replace
   `waiting.WaitAsync(TimeSpan.FromSeconds(5))` with
   `Eventually.CompletesAsync(waiting, "the inbox did not end when the hub stopped")`.

   This is correct whether or not the request has reached `InboxAsync` when `StopApplication()` is
   called: a request that arrives after shutdown has begun finds `ApplicationStopping` already
   cancelled, so `Task.Delay` throws at once and the method returns `TimedOut: true` — the same answer.

After this, `grep -n "Task.Delay" tests/Muthur.Server.Tests/*.cs` matches only inside `Eventually.cs`.

### `ConductorTests` — exact changes

Add one helper to `tests/Muthur.Server.Tests/HubTestExtensions.cs`:

```csharp
/// <summary>The ledger once <paramref name="settled"/> holds — the conductor writes its outcome events from a detached task.</summary>
public static Task<IReadOnlyList<EventDto>> EventsWhenAsync(this HubFactory hub,
    Func<IReadOnlyList<EventDto>, bool> settled, string because);
```

It polls `Routes.Events` as the founder through `Eventually.TrueAsync`, and returns the first snapshot
for which `settled` is true. Every assertion below then runs against that one snapshot, so a positive
and a negative assertion never see different reads.

Each site below replaces its `GetFromJsonAsync(Routes.Events, ...)` with an `EventsWhenAsync` whose
predicate is the **positive** fact the test is waiting for; the negative assertions (`DoesNotContain`)
then run unchanged against the returned snapshot. A negative can never be the thing waited on.

| Test | Predicate to wait on | `because` |
|---|---|---|
| `A_task_that_has_run_out_of_attempts_is_not_staffed_again` (line ~186) | `e => e.Any(x => x.Type == "conductor.exhausted")` | `"the conductor never recorded that it had run out of attempts"` |
| `...stalled...` (line ~223) | `e => e.Count(x => x.Type == "conductor.failed") == 3` | `"three launch failures were never recorded"` |
| `A_probe_that_fails_re_arms_the_cooldown_without_shouting_again` (line ~276) | `e => e.Count(x => x.Type == "conductor.failed") == 6` | `"six launch failures were never recorded"` |
| `A_session_that_starts_again_clears_the_failures_behind_it` (line ~317) | `e => e.Count(x => x.Type == "conductor.failed") == 2` | `"two launch failures were never recorded"` |
| `A_run_that_hangs_is_recorded_as_a_session_that_failed...` (line ~435) | `e => e.Count(x => x.Type == "conductor.session_failed") == 2` | `"two session failures were never recorded"` |
| `A_launch_failure_from_the_real_launcher_is_worded_as_one` (line ~489) | `e => e.Count(x => x.Type == "conductor.failed") == 2` | `"two launch failures were never recorded"` |
| `An_unexpected_failure_is_called_a_launch_failure_rather_than_a_session` (line ~507) | `e => e.Count(x => x.Type == "conductor.failed") == 1` | `"the launch failure was never recorded"` |

Line numbers are where these sit today; find them by test name, not by number.

Two further sites in the same file read `Conductor.StatusAsync().LastAction`, which the same detached
task sets (`"gave up running"` at line ~438, `"gave up starting"` at line ~493). Both already sit after
an `EventsWhenAsync` from the table above; move each `Assert.Contains(...)` on `LastAction` to **after**
that call so the event wait orders it. No other change to those assertions.

`conductor.on` / `conductor.off` (line ~569) are written by the founder's own request before it returns
and are not detached — leave them, and leave `Assert.Equal(n, _hub.Validators.Started.Count)` and
`Assert.Empty(_hub.Validators.Started)` everywhere, which are settled synchronously (see Context).

### The rule, written down

Add to the `## Rules of the codebase` section of `CLAUDE.md`, as the last bullet of the `Tests:` bullet
or immediately after it, one sentence:

> Tests never sleep to synchronize: real time is only ever a hang-detector budget (`Eventually`), and
> anything a test waits for is a condition it can observe or a step of the fake clock.
