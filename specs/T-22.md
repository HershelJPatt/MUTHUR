# T-22 — The server test suite is flaky under load

> Frozen spec. An implementer completes this without making design decisions.
> If something here is wrong or missing, the implementer stops and reports; they do not improvise.

## Goal

After this task, `tests/Muthur.Server.Tests` contains no test that uses elapsed wall-clock time as a
synchronization barrier, and no test that asserts on work a detached (fire-and-forget) task has not
been observed to finish. A validator who runs `dotnet test` on a loaded machine and sees red can trust
that the red is about the change under validation.

This matters because every validator treats `dotnet test` as ground truth. A suite that fails for
reasons unrelated to the change teaches validators to re-run until green, which is the habit that lets
a real regression through — and an unattended conductor-started validator cannot decide to re-run at all.

## Context

### What was reproduced, and how

The flake is real and now has a recipe. On a 24-core Windows box, twelve runs of the server suite at
six-way concurrency (six `dotnet test` processes at a time, two passes) produced one failure:

```
[xUnit.net 00:00:25.81]     Muthur.Server.Tests.MessagingTests.A_waiting_inbox_times_out_empty [FAIL]
Failed!  -  Failed: 1, Passed: 138, Skipped: 0, Total: 139
```

Eighteen runs at one- and three-way concurrency before that were all green, which is why this only shows
up when a machine is busy.

### The mechanism, exactly

`MessageService.InboxAsync` computes its deadline **when the request reaches the server**:

```csharp
var deadline = clock.GetUtcNow() + TimeSpan.FromSeconds(Math.Clamp(waitSeconds, 0, MaxWaitSeconds));
```

`MessagingTests.A_waiting_inbox_times_out_empty` starts the call, sleeps 150 ms of real time, and then
advances the fake clock once:

```csharp
var waiting = InboxAsync(waiter, wait: 60);
await Task.Delay(150);
_hub.Clock.Advance(TimeSpan.FromSeconds(61));
var inbox = await waiting.WaitAsync(TimeSpan.FromSeconds(10));
```

On a loaded machine 150 ms is not enough for the request to reach `InboxAsync`. The clock then moves
*before* the deadline is computed, so the deadline lands 61 s further out than the test believes, the
advance is consumed by nothing, and the poll waits for fake time that never comes. Ten real seconds
later `WaitAsync` throws and the test fails. There is no second advance, so the test can never recover.

`Task.Delay(150)` appears three more times in the same file with the same intent — "give the server a
moment" — and the real-time budgets on the `WaitAsync` calls (5 s and 10 s) are tight enough that a
loaded machine can exceed them on their own.

### The second shape: detached work asserted synchronously

`ConductorService.RunPassAsync` deliberately does not wait for the sessions it staffs:

```csharp
_ = RunSessionAsync(assignment, key);
```

`RunSessionAsync` calls the launcher, and on failure takes `lock (_launchFailures)` and updates the
failure count **before** its first `await`; so both `FakeValidatorSessions.Started` and the stall
bookkeeping are settled by the time `RunPassAsync` returns. That part is safe and must not be changed.

What is *not* settled is the ledger event: `conductor.failed`, `conductor.session_failed` and
`conductor.stalled` are written by `await ledger.MutateAsync(...)` inside that detached task, and so is
`_lastAction`. `ConductorTests` reads all of them immediately after the last pass returns. On an idle
machine the continuation almost always wins the race; under load it need not. This has not been observed
failing, and it is the same class of defect as the one that was.

## Design

### The rule

A test may spend real time only as a **hang detector**: a budget generous enough that a loaded machine
never reaches it, whose expiry means the system has genuinely stopped making progress. A test may never
spend real time as a **barrier**: "sleep n milliseconds, by which point the server will have got there".

### New file: `tests/Muthur.Server.Tests/Eventually.cs`

```csharp
namespace Muthur.Server.Tests;

/// <summary>
/// Waiting without wall-clock guesses. Every budget here is a hang detector, not a pace: generous enough
/// that a loaded machine never trips it, so a test that does trip it has really stopped making progress.
/// </summary>
internal static class Eventually
{
    /// <summary>The real-time ceiling for anything a test waits on.</summary>
    public static readonly TimeSpan Budget = TimeSpan.FromSeconds(60);

    /// <summary>Returns once the condition holds, or fails naming what never became true.</summary>
    public static Task TrueAsync(Func<bool> condition, string because);

    /// <summary>Returns once the probe answers non-null, or fails naming what never arrived.</summary>
    public static Task<T> TrueAsync<T>(Func<Task<T?>> probe, string because) where T : class;

    /// <summary>Awaits a call that something else is expected to complete, within the budget.</summary>
    public static Task<T> CompletesAsync<T>(Task<T> call, string because);

    /// <summary>
    /// Awaits a call that ends when a server-side deadline passes, pushing the fake clock by
    /// <paramref name="step"/> until it does. The server computes that deadline when the request reaches
    /// it, which a test cannot observe, so the advance is repeated rather than done once.
    /// </summary>
    public static Task<T> AfterAdvancingAsync<T>(Task<T> call, FakeTimeProvider clock, TimeSpan step, string because);
}
```

Behaviour:

- Poll interval is 10 ms. The budget is measured with `DateTime.UtcNow` — this is the test harness's own
  stopwatch, not server or core code, so the injected-`TimeProvider` rule does not apply; no other
  `DateTime`/`DateTimeOffset` reading may be added to the test project.
- On expiry every method throws `Xunit.Sdk.XunitException` with the message
  `$"Waited {Budget.TotalSeconds:0}s and {because}"`. `because` is written to complete that sentence,
  e.g. `"the inbox never returned"`.
- `AfterAdvancingAsync` advances the clock once per poll and returns `await call` once `call.IsCompleted`.
  Advancing repeatedly is safe: the hub under test runs with `Muthur:BackgroundServices=false`, so
  nothing else is watching the clock.
- `CompletesAsync` wraps `call.WaitAsync(Budget)` and converts `TimeoutException` into the message above.
- Cancellation, configurable budgets and per-call overrides are deliberately absent. One budget, one
  poll interval.

## Amendment 1 — the shutdown test needs an observable barrier (2026-09-18)

The first version of this spec told the implementer to delete `await Task.Delay(150);` from
`A_waiting_inbox_ends_the_moment_the_hub_stops`, on the reasoning that a request arriving after
`StopApplication()` would find `ApplicationStopping` already cancelled and return `TimedOut: true`
anyway. **That reasoning was wrong.** The implementer found it, and it was reproduced here: with the
delay removed the test fails *deterministically*, 1 run in 1 and 5 in 5, not intermittently.

`StopApplication()` on a `WebApplicationFactory` host does not merely signal `ApplicationStopping`; the
host shuts down and disposes the root service provider while `TestServer` still accepts and dispatches
the in-flight request. The request is therefore not "late into `InboxAsync`" — it is dispatched into a
hub whose DI container is gone, and the pipeline answers before `MessageService.InboxAsync` runs at all:

```
STATUS 500
{"code":"internal_error","message":"Cannot access a disposed object. Object name: 'IServiceProvider'."}
```

`MessageService.InboxAsync`'s shutdown handling is correct and is not the problem. The test genuinely
must not call `StopApplication()` until the request has reached the long-poll wait, and 150 ms of real
time is the wrong way to know that. So the barrier stays and becomes observable.

### `HubFactory.Clock` becomes an observing clock

`tests/Muthur.Server.Tests/HubFactory.cs` may be modified for this — the earlier "do not change
`HubFactory`" instruction covers `Dispose` and its `ClearAllPools()` call only, and that still stands.

Add to `HubFactory.cs`, beside the other fakes:

```csharp
/// <summary>
/// A fake clock that also records what has started waiting on it. A test cannot otherwise observe that a
/// long-poll request has reached the hub, and the request's own wait is what creates the timer.
/// </summary>
public sealed class ObservingClock(DateTimeOffset start) : FakeTimeProvider(start)
{
    private readonly List<TimeSpan> _timers = [];

    /// <summary>The due time of every timer created on this clock, in the order they were created.</summary>
    public IReadOnlyList<TimeSpan> Timers { get { lock (_timers) return [.. _timers]; } }

    public override ITimer CreateTimer(TimerCallback callback, object? state, TimeSpan dueTime, TimeSpan period)
    {
        lock (_timers) _timers.Add(dueTime);
        return base.CreateTimer(callback, state, dueTime, period);
    }
}
```

and change `HubFactory.Clock` to
`public ObservingClock Clock { get; } = new(new DateTimeOffset(2026, 1, 1, 12, 0, 0, TimeSpan.Zero));`.
`ObservingClock` derives from `FakeTimeProvider`, so every existing `_hub.Clock.Advance(...)`,
`_hub.Clock.GetUtcNow()` and every `Eventually.AfterAdvancingAsync(..., _hub.Clock, ...)` call keeps
compiling and behaving identically. Nothing else changes. If `FakeTimeProvider` turns out not to be
derivable, or `CreateTimer` not overridable, **stop and report** rather than inventing a substitute.

### The test

```csharp
[Fact]
public async Task A_waiting_inbox_ends_the_moment_the_hub_stops()
{
    var waiter = await _hub.RegisterAgentAsync("idle");
    var waiting = InboxAsync(waiter, wait: 900);
    // The hub must be told to stop only once the request is really parked in the long poll: a request
    // dispatched after StopApplication() meets a disposed service provider, not a cancelled wait.
    await Eventually.TrueAsync(() => _hub.Clock.Timers.Contains(TimeSpan.FromSeconds(900)),
        "the inbox never reached its 900-second wait on the hub's clock");
    Assert.False(waiting.IsCompleted);

    _hub.Services.GetRequiredService<IHostApplicationLifetime>().StopApplication();

    var inbox = await Eventually.CompletesAsync(waiting, "the inbox did not end when the hub stopped");
    Assert.True(inbox.TimedOut);
    Assert.Empty(inbox.Messages);
}
```

The clock is frozen for the whole test and `InboxAsync` is called with `wait: 900`, so the only timer
that can carry a 900-second due time is this request's own `Task.Delay(remaining, clock, ...)`. That is
what makes this barrier exact where a timer *count* would only be suggestive.

The acceptance check is unchanged and now really holds: after this,
`grep -rn "Task.Delay\|Thread.Sleep" tests/ --include=*.cs` matches only inside `Eventually.cs`.

## Amendment 3 — `ClearAllPools()` is the third flake, and I had cleared it wrongly (2026-09-18)

`conductor-validator` failed T-22 at `df8d7fd`: in a 24-run matrix,
`OutboundTests.A_failure_whose_os_message_names_part_of_the_address_reveals_nothing` failed **registering
an agent** with HTTP 500, 138 passed / 1 failed. The TRX records:

```
ObjectDisposedException: Cannot access a disposed object. Object name: 'SQLitePCL.sqlite3'
   at Microsoft.Data.Sqlite.SqliteConnection.Open()
   POST /api/v1/agents/register
```

That is not a timing barrier and not detached work. It is `HubFactory.Dispose` calling the
**process-global** `SqliteConnection.ClearAllPools()`. When one test class finishes, it disposes the
pooled connections of *every* hub in the process, including hubs still serving requests. A hub that is
midway between renting a pooled connection and opening it gets its handle disposed underneath it, and
answers 500 on whatever request happened to be in flight. The failing test is arbitrary, which is why
the original report on `main` named a different one.

### Why the first probe cleared it, and why that probe was worthless

The retracted section above rested on a probe with **one** connection string and long-held write
transactions. One pool, almost never idle, so there was almost nothing for `ClearAllPools` to dispose
mid-rent — it measured the wrong thing and returned a confident zero. The suite has one pool per hub and
short-lived connections, which is exactly where the race lives.

Re-probed against the real shape — 12 distinct databases, each opening and closing pooled connections,
another thread calling `ClearAllPools()` every 3 ms:

```
4163 opens, 1 ObjectDisposedException — message identical to the validator's TRX
```

A third probe modelled the suite honestly (hubs serve in bursts, then tear down, staggered, while others
keep serving) and compared the candidates:

```
today: ClearAllPools()      opens=2695   objectDisposed=2   other=0
fix A: ClearPool(own)       opens= 825   objectDisposed=0   other=0
fix B: Pooling=False        opens=2863   objectDisposed=0   other=0
```

Note what fix A does **not** prove: a second probe that cleared each hub's own pool while that hub was
still serving produced 3 `ObjectDisposedException`s in 4243 opens. `ClearPool` is only safe because a
hub has stopped serving by the time it tears down — a safety that rests on an assumption about
`WebApplicationFactory`'s disposal order. That is the same kind of assumption that produced the
retracted section.

### The fix: fix B

`ClearAllPools()` exists only so the temp data directory can be deleted while file handles are still
held by the pool. With pooling off, `SqliteConnection.Dispose` really closes the file and there is
nothing to clear — the race is removed rather than narrowed, and no global state is touched.

In `tests/Muthur.Server.Tests/HubFactory.cs`:

1. In `ConfigureWebHost`, beside the existing `UseSetting` calls, add:

   ```csharp
   // Pooling off, not pool-clearing: the process-global ClearAllPools() disposed connections out from
   // under hubs that were still serving, which failed an arbitrary test with a 500 under load.
   builder.UseSetting("Muthur:ConnectionString",
       $"Data Source={Path.Combine(DataDir, MuthurEnvironment.DatabaseFile)};Pooling=False");
   ```

   `MuthurOptions.ResolveConnectionString()` returns `ConnectionString` when it is set, so this is the
   connection string the whole hub uses. `DataDir` stays as it is.

2. In `Dispose`, delete the `SqliteConnection.ClearAllPools();` line. Keep the `Directory.Delete` and
   both of its `catch` clauses exactly as they are.

3. Remove `using Microsoft.Data.Sqlite;` if nothing else in the file needs it (warnings are errors).

Nothing else changes. No file under `src/` changes.
