# T-99 — Bind approval to the exact validation subject

> Frozen specification, revision 3. Base: main 89dc34c. Stop and report any missing design decision.

## Goal
Bind every new validation claim and verdict to one immutable implementation/spec/policy subject and round; only that approved commit can land. Preserve independent review and expose unknown historical provenance with explicit recovery.

## Context
LifecycleService currently records head only in an event, deletes current validation rows on resubmission, and GitLander merges a moving branch. TaskService.SetSpecAsync reads committed spec content. Ledger.MutateAsync serializes all writes. Contracts are AOT serialized; new DTOs must be registered. Follow CLAUDE.md. T-95 is done; T-67/T-88/T-97 remain separate unresolved Claude permission/authentication work, with no permission changes authorized here. Use only the available implementer tier, one worker at a time. No model calls in hub.

## Non-goals
Merge-result validation, remote deployment, changed validator independence, new permissions/accounts/budgets, protected agent definition edits, and claiming completion of a live pilot before integration.

## Design
### Durable subject
Add a nullable current validation subject to WorkTask and nullable subject ID to TaskValidation. Use a new immutable ValidationSubject entity/table with GUID Id (also round identity), TaskId, ProjectId, repository identity (canonical full repository path), implementation full commit SHA, SpecPath, SpecSha256 (UTF-8 exact committed text), canonical JSON required validator role keys (ordinal sorted distinct), canonical JSON required checks and environment inputs, and CreatedAt. The subject ID uniquely identifies a round even if all content repeats. Persist the full subject in task.implemented and validation claimed/verdict events as well as durable rows. TaskDto exposes current subject and provenance status; ValidationDto exposes subjectId and evidenceStatus. History stays in append-only ledger when current rows are replaced.
Required checks snapshot the committed muthur.project.json build and test command values (missing config means empty checks, malformed config is actionable refusal). Relevant invalidating environment inputs are repository/project identity, default branch, landing mode, required validators and their current brief content hashes. Descriptive metadata (OS description, architecture, runtime version, host hub revision if already available) is recorded separately and never alone invalidates approval. At claim, verdict and land, current check-command policy is read from the subject implementation SHA, never the moving task/default branch or working tree. These commands are part of the reviewed implementation. Current project identity/path/default branch/landing mode/required roles and brief hashes come from the live ledger and must match the snapshot. Changes on the task branch are refused by the landing head comparison; unrelated default-branch config changes do not retroactively change this subject. No secret values or arbitrary environment dumps. Subject DTO fields explicitly distinguish these categories.
Compute subject at implementation time from the resolved SHA, including spec/config reads by that SHA rather than branch name. Require spec file present and belonging to task using existing heading rule. Snapshot and verify all task/policy inputs under the ledger mutation; do not combine pre-read task data with changed policy/spec. Hash frozen spec when attached; fail implementation with spec_changed if the submitted commit differs from attached frozen content, directing owner to explicitly reattach spec. Older attached specs with unknown digest must be explicitly reattached. Store newly attached digest durably. New round starts on every implementation submission.
### Claims, verdicts, compatibility
Extend ClaimValidationRequest and VerdictRequest with nullable SubjectId; claim may omit it to take current round, returning full subject; if supplied it must match. Verdict requires explicit SubjectId for all outcomes (validation_subject_required, HTTP 422 / CLI exit 2); never auto-fetch a current subject at verdict time. CLI validate yes/no/blocked accepts --subject <guid>. CLI claim returns subject; conductor validator prompt and kit source validation instructions tell validators to retain it, inspect the exact SHA and submit that identifier. Do not modify installed/protected .claude definitions.
Reject mismatched/closed round with stale_validation_subject (409 / exit 3) before recording a verdict. Preserve role/owner/claim gates. Claim is tied to subject in row/event, and no superseded claim may confer authority. All required pass rows must carry the current subject ID and useful evidence before validated or land can succeed. Freeze role/check policy in subject and compare current policy at claim, verdict and land: a changed policy returns validation_subject_changed with explicit revalidation instructions. Spec attachment while validated/validating remains disallowed: use recovery first. Branch edits to spec or any other file cannot substitute a different commit.
Evidence is required on every outcome: stable evidence_required (422 / exit 2) for null/empty/whitespace, actionable message naming --evidence/--evidence-file and expected content. Existing evidence text is an evidence reference/report, not machine proof: retain freeform reports but reject single-token acknowledgments (ok, pass, yes, done; case-insensitive). Require a trimmed report of at least 20 characters describing check, observation and an artifact/reference or reproduction command; this minimum is explicitly a presence/quality prompt, not correctness validation. CLI --evidence-file reads a local UTF-8 report and sends its contents; mutually exclusive with --evidence. Do not fetch arbitrary evidence URLs. Existing valid failure/blocked reports keep working.
Legacy subjects remain null, historical verdict/evidence/events unchanged. Return provenanceStatus unknown for legacy, current for compatible current subject, stale for invalidated round; evidenceStatus missing/reported/stale/unknown without claiming correctness. Never infer a historical subject from old events. Add owner/founder-only task revalidate <id> --reason <text> via POST task action revalidate: from validating/validated/in_progress only, return to in_progress, clear claims and current subject, retain verdict/history, record invalidation reason, renew owner lease. Owner attaches spec and runs implemented again to open a fresh round. Legacy landing refuses validation_provenance_unknown with exact recovery steps. Done/cancelled historical tasks remain done/cancelled and readable. Read surfaces include CLI JSON, API and task detail dashboard with current SHA/spec digest/round and missing/stale/unknown evidence labels, and clear recovery help. Keep normal queue staffing functional; avoid endlessly staffing legacy unknown rounds by excluding them with clear recovery indication.
### Landing and concurrency
GitLander must consume the subject implementation SHA, never a mutable branch for merge inputs, parent creation, ancestor checks or conflict history. First compare branch head to subject SHA; mismatch returns implementation_changed without merging. If branch moves after comparison, merge still consumes only SHA. Non-checkout merge-tree uses captured target SHA and implementation SHA, commit-tree same exact parents, update-ref compare-and-swap target. Checkout merge uses implementation SHA and preserves dirty-checkout refusal and abort-on-conflict. Add deterministic injected process barriers to race tests; no sleeps.
Prevent owner resubmission/spec/policy mutation overlapping approval check and git integration: execute final validation of current subject and lander call and outcome recording within one Ledger.MutateAsync critical section, retaining landing semaphore, no nested ledger calls. This intentionally holds writer during bounded git work for first slice, document tradeoff. Subject/state checked before git; all writes serialized until outcome recorded. Read helpers may use passed Db but not reenter ledger. Conductor uses identical service gate. For PR projects use a round-specific branch refs/heads/muthur-approved/<task>/<subject-id> at the approved SHA, push an explicit SHA refspec without force and open that pinned branch; record subject in PR body. Preserve existing outbound authority, do not add new remote calls. Tests use fake opener/runner, no real outbound.
### Events and observation
Record refused stale verdict and missing evidence attempts through ledger with task and subject IDs where supplied, excluding report content from refusal events; maintain stable error response after committing refusal event. Record subject invalidations/revalidation requests and landing subject. Document a reproducible count query over ledger event types rather than overlapping throughput counters. Add docs/T-99-validation-subject.md covering migration/recovery, version compatibility (old clients must upgrade and explicitly provide subject), and rollout/pilot checklist. First real-use pilot is next eligible post-install task; record unavailable as missing, never completed. The orchestrator will create a linked observation follow-up if unavailable at submission.
