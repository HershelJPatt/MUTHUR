# T-4 — Discord is a channel the organization can hear on, not only speak into

> `discord-webhook` has been an outbound target since M8. Nothing arrives from Discord. The founder wants to
> reach the organization, and be reached by it, from a phone.

## What is there today

**Out**: `DiscordWebhookChannel` (`OutboundChannels.cs:27`) posts to a webhook URL, 2000 characters, through the
outbound gate like everything else. This side is finished and this task does not change it.

**In**: `IInboundSource` is `Scheme` plus `FetchAsync(location, cursor)` returning
`SourceFetch(IReadOnlyList<IncomingItem>, Cursor)`. `GitHubIssuesSource` is the only implementation. Ingest is
deliberately **pull-based with a cursor** — the hub is off for hours and never relies on being told anything, so
webhooks are not an option for the inbound direction.

`GitHubIssuesSource` authenticates by shelling out to `gh`, which already holds the user's login. Discord has no
such CLI: it needs a bot token of our own.

## Design

### The source

`DiscordChannelSource`, scheme `discord`. Location is a channel id, or `<guildId>/<channelId>`.

```
muthur project set my-repo --ingest discord:1234567890 --founder
muthur project set my-repo --ingest discord:987654321/1234567890 --founder
```

`GET https://discord.com/api/v10/channels/{channel}/messages?limit=100[&after={cursor}]` with header
`Authorization: Bot {token}`, through `IHttpClientFactory` like the webhook channel. A non-success response
throws `InvalidOperationException`, which `IngestService` already turns into `ingest.failing` and retries at
the next interval — rate limits and an expired token both land there.

### The token

`Muthur:DiscordBotToken`, read from `MuthurOptions` like every other setting, and in practice set as the
environment variable `Muthur__DiscordBotToken`. It is never written to the ledger, never logged, and never
returned by any endpoint. With no token configured, a `discord:` source fails with a message saying which
variable to set — it does not fail silently and it does not log the value it did not find.

### The message loop, which is the part that can go wrong

`comms-oncall` replies into the same channel through the webhook. Those replies are messages in that channel,
and the next poll would ingest them as new inbound items, which the on-call would then triage, and reply to.

**Every message whose `author.bot` is true is skipped.** Webhook messages carry `webhook_id` and `author.bot`,
so the one rule covers our own replies, other bots, and anything posted by an integration. Only what a person
typed becomes inbound. This is the single most important line in the adapter and it is tested directly.

### Cursor and ordering

The cursor is a Discord snowflake — the highest message id seen. Snowflakes are **compared as `ulong`, never as
text**: they are ids, not timestamps, and string comparison gives the wrong answer the day their digit count
changes. Discord returns newest first; items are sorted ascending by id before they are returned, so they land
in the order they were written and the cursor advances to the true maximum.

### Mapping a message

`IncomingItem(ExternalId, Title, Body, Url, Author)`:

- `ExternalId` — the message id. Ingest already de-duplicates on it, so a re-poll is harmless.
- `Title` — the first line of the content, trimmed, cut to 120 characters with an ellipsis.
- `Body` — the full content.
- `Author` — the author's username.
- `Url` — `https://discord.com/channels/{guild}/{channel}/{message}` when the location carries a guild, else null.

A message with no text after trimming (an attachment or a sticker alone) is skipped. The gate reasons about
text, and an inbound item with no words in it is nothing an on-call can act on.

## Out of scope

Threads, reactions, edits and deletes — a message is ingested once, as it read when it was first seen. DMs.
Slash commands. Any change to the outbound side.

## Verification

```
dotnet build && dotnet test
```

`DiscordChannelSourceTests` (new, in `Muthur.Server.Tests`) drives `DiscordChannelSource.Parse` over recorded
payloads, the way `GitHubIssuesSource.Parse` is tested:

- a message from a person becomes an item; **a message with `author.bot: true` does not** — nor does one
  carrying `webhook_id`, which is how our own replies come back;
- items come out ascending by id from a newest-first payload, and the cursor is the highest id;
- a cursor of `999999999999999999` and an id of `1000000000000000000` order correctly — the digit-count case
  that string comparison gets wrong;
- content of `""` or whitespace is skipped;
- title is the first line, cut at 120 characters; body keeps everything;
- the deep link appears only when the location carries a guild.

End to end, against a scratch hub, with `Muthur__DiscordBotToken` set to a real bot token and a private channel
the founder owns:

1. `project set <p> --ingest discord:<guild>/<channel> --founder`, post a message as a person →
   `muthur inbound list` shows it after a poll, with the author, the deep link, and the text.
2. `inbound claim <id> --as-task` → a backlog task linked to it.
3. Draft a reply to a `discord-webhook` target for that channel, have a second agent review it, send it → it
   appears in Discord, and **the next poll does not ingest it**. `inbound list` gains nothing.
4. Unset the token → the source reports `ingest.failing` with a message naming the variable, and the rest of
   ingest keeps working.
