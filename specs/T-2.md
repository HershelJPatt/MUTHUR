# T-2 — The kit ships an on-call roster, and re-installing it never destroys a brief

> A role is a lease plus a brief. MUTHUR has shipped the lease since M4 and has never shipped a brief.
> Every founder invents the roster from scratch, and the ones who don't get a validation gate that
> does nothing.

## What is there today

`kit install` is a manifest copier (`src/Muthur.Cli/Commands/KitCommands.cs`): each `kit.json` entry names a
`from` under the harness directory and a `to` in the target repository, with `mode` `replace` (default) or
`section`. `{{core:<file>}}` expands from `kit/core/`.

`kit/core/oncall.md` and `kit/core/validate.md` are the **procedures**: how to hold a role, how to validate,
generic across every product. They ship today and they are good.

A **brief** is the other half — how to build, launch and drive *this* product, and what evidence this
organization accepts. `kit/core/validate.md` step 2 sends the agent to `muthur role brief <role>` for exactly
that. Nothing ships one. `kit/briefs/` holds a single file, `muthur-win-validator.md`, which is this
repository's own brief for its own role; no manifest references it, so `kit install` has never written it.

So a new repository gets procedures that say "read your brief" and no brief to read.

## Design

### Naming

`kit/briefs/<role>.md` is a **starter** brief, shipped to target repositories.
`kit/briefs/<project>-<role>.md` is a real brief for a real project, kept here because this repository is
also a MUTHUR project. `muthur-win-validator.md` stays exactly where it is; it is not a starter and no
manifest references it.

### Four starter briefs

Written to `briefs/<role>.md` in the target repository, matching the README's `--brief-file briefs/win.md`.

- `briefs/validator.md` — the largest. A validator brief is inherently product-specific, so this one ships the
  parts that are not: the live-hub / build-under-test separation and the rule never to export `MUTHUR_HOME` or
  `MUTHUR_URL`, the standard of evidence (what you ran and saw, never a reading of the diff), the obligation to
  report blocked rather than pass when the product cannot be driven, and cleanup. The product-specific parts —
  build, launch, drive, what healthy looks like, where the logs are — are headed sections each carrying one
  `TODO(founder):` line saying what belongs there.
- `briefs/comms-oncall.md` — holds the outbound channels. Triages what arrives, turns real work into tasks,
  drafts replies into the gate, never decides a founder-level question. Generic; usable as shipped.
- `briefs/observability-oncall.md` — watches logs and error rates, files what it finds as tasks with a
  reproduction. Points at `muthur.project.json` for where the logs are.
- `briefs/release-oncall.md` — owns landing and the release runbook; refuses to land on a dirty default branch.

Each opens with one line naming the role and closes with what "done for today" looks like.

### A third write mode: `create`

`WriteFile` always replaces. The README promises `kit install` is "safe to re-run", and it is — for files
MUTHUR owns. A brief stops being MUTHUR's the moment the founder edits it, and edited briefs are the whole
value of the feature. Re-running the install must not silently overwrite one.

`mode: "create"` writes the file only when it is absent. Status is `created` when it wrote, `kept` when a file
was already there. All four briefs use it in all three manifests (`claude`, `codex`, `generic`).

### Telling the founder what to do next

A brief on disk does nothing until a role exists. The install result gains a `roles` array — one entry per
brief actually present in the repository after the install, each with its `role` key and the exact `define`
command:

```json
"roles": [
  { "role": "validator", "brief": "briefs/validator.md",
    "define": "muthur role define validator --brief-file briefs/validator.md --founder" }
]
```

Keys come from the brief's filename. Nothing is defined automatically: a role is the founder's to create, and
`role define` needs `--founder` for that reason.

## Out of scope

Requiring validators on a project, or warning when none are set — that is T-5. Rewriting
`muthur-win-validator.md`, including its stale `C:\src\Experiment` repository path.

## Verification

```
dotnet build && dotnet test         # 0 warnings; Muthur.Cli.Tests covers the three write modes
```

`tests/Muthur.Cli.Tests` is new (there was no home for CLI tests). It drives `KitCommands.WriteKitFile`
against a temp directory: `replace` overwrites and reports `updated`, `replace` on identical content reports
`unchanged`, `create` writes an absent file and reports `created`, `create` over an existing file leaves the
bytes alone and reports `kept`.

End to end, against a throwaway repository and a scratch hub (own `MUTHUR_HOME`/`MUTHUR_URL`, an installed
CLI under `artifacts/`):

1. `kit install --harness claude` in an empty git repository → the four briefs appear under `briefs/`, each
   `created`; the result's `roles` array carries four `define` commands.
2. Edit `briefs/validator.md`; run `kit install` again → status `kept` and **the edit survives byte for byte**.
   The procedure files under `.claude/` still report `unchanged` or `updated`.
3. Run one of the printed `define` commands against the scratch hub, then `role brief validator` → the brief
   comes back from the hub.
4. `kit install --harness codex` and `--harness generic` into their own repositories → the same four briefs.
