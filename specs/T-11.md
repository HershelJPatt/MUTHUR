# T-11 — The conductor staffs validation, so a passing task needs nobody

> Scoped deliberately to **validators only**. That is the half that removes the founder from the loop for every
> task that passes, and the half with an unambiguous success condition: a task reaches `validating` while nobody
> is watching, and is `validated` or failed-with-evidence by morning.

## Why this is not `muthur worker run`

`WorkerLauncher` (`src/Muthur.Launch/WorkerLauncher.cs:20`) scrubs `MUTHUR_AGENT` and `MUTHUR_TOKEN`:

> Hub identity never reaches a worker: workers have no authority in the organization.

That rule is correct and this task must not weaken it. A worker implements a frozen spec in a worktree and reports
to its orchestrator; it cannot claim, land, or vote. A **validator is the opposite**: it holds a role, reads a
task, and casts a verdict that decides whether work ships. It needs identity.

So there are two kinds of launched session, and the difference is authority. This task names that difference in
code rather than leaving it implicit in one launcher that does both.

## Design

### `AgentLauncher` — a session that acts *as* somebody

A sibling of `WorkerLauncher` in `Muthur.Launch`, sharing the adapters and the candidate/rate-limit logic:

| | `WorkerLauncher` | `AgentLauncher` |
|---|---|---|
| `MUTHUR_AGENT` / `MUTHUR_TOKEN` | scrubbed | **set** |
| `muthur` commands | denied | allowed |
| Working directory | a worktree made for it | the project's repository root |
| Worktrees | given one | makes its own, as the validate procedure says |
| Reports by | printing to its launcher | calling the hub itself |

The agent it acts as is registered by the conductor, with its own token, exactly as a human-started session would
be. Nothing about a conductor-started validator is privileged over one the founder starts in a terminal.

### `ConductorService`

A `BackgroundService` beside `IngestWorker`. Each pass, inside one `Ledger.ReadAsync`:

1. Tasks in `validating`.
2. For each, the required validator roles with no `yes` yet **and no live holder**.
3. Skip any task that is `blocked`, and any role already held — the hub's leases refuse a second holder, and the
   conductor must not use that refusal as flow control.
4. Up to the remaining concurrency budget, launch one validator session per (task, role).

The bounce-back loop needs no new states: a failed task is already back with its owner, and if that session has
exited its claim lapses, so the task is unclaimed and staffable again. **The conductor adds no state to the
machine it serves.**

### Choosing who validates

From the tier catalog, `mastermind` candidates whose account is not limited. Prefer a candidate whose **harness
differs from the one that built the task** — read from the `task.implemented` event's `actorModel`. The same idea
as `RequireCrossProviderReview` in the outbound gate, applied to validation: Codex checks what Claude wrote.

Preference, not a rule. If the only candidate left is the same harness, validating is better than not.

### What the founder controls

```
muthur conductor status              # on/off, budget, what it has running, what it last did
muthur conductor on | off --founder  # recorded in the ledger like any other founder decision
```

`Muthur:ConductorEnabled` (default **false** — it does not start staffing because someone upgraded),
`Muthur:ConductorMaxSessions` (default 2), `Muthur:ConductorSessionMinutes` (default 45).

The founder has said unattended spending is allowed, so there is no separate night budget. `agent limited` is
still respected: a limited account leaves the rotation, and if no candidate remains the conductor stops rather
than degrading to a tier it was not asked for.

### Not looping forever

A task whose validation fails is restaffed on the next pass. Left alone that is a crash loop, spending a
subscription all night on the same failure.

Count `validation.failed` events per task. At **three**, the conductor stops staffing it and raises a founder
request naming the task and the three verdicts. A repeated failure is a judgment call, and judgment calls go to
the founder — which is the same rule the rest of this system already follows.

## Out of scope

Staffing **orchestrators**. Today the founder's `/loop` is what starts an orchestrator, and that works; adding a
second mechanism before validators are proven would make two things unproven instead of one. Nested fleets (T-19).
Any change to `worker run` (T-15).

## Verification

```
dotnet build && dotnet test
```

New tests in `Muthur.Server.Tests` against the real HTTP API through `HubFactory`, with a fake launcher recording
what it was asked to start:

- a task in `validating` with an unheld required role → one launch, for that task and role;
- the same task with the role **held by a live agent** → no launch;
- a `blocked` task → no launch;
- two tasks and `ConductorMaxSessions=1` → one launch, not two;
- a task whose `implemented` event names `claude` → the chosen candidate is `codex` when both are available, and
  `claude` when Codex's account is limited;
- three `validation.failed` events on a task → no further launch, and a founder request exists naming it;
- `ConductorEnabled=false` → no launches at all;
- `conductor off` by the founder is in the ledger and takes effect on the next pass.

Unit tests in `Muthur.Launch.Tests` for `AgentLauncher`: the environment it builds **contains** `MUTHUR_AGENT` and
`MUTHUR_TOKEN` (the inverse of the worker case, which is asserted alongside it so the two can never quietly
converge), and `muthur` is in the allow list rather than the deny list.

End to end, against a scratch hub with a real repository and `ConductorEnabled=true`:

1. Drive a task to `validating` with a required validator role that nobody holds. Without touching anything else,
   a validator session starts, takes the role, and the task reaches `validated` or fails with evidence.
2. Kill the validator session mid-run; the role lease lapses and the next pass restaffs it.
3. `conductor off`, drive another task to `validating`, confirm nothing starts.

## Round 2 — what validation found

`docs-validator` failed round 1 with four defects. Build, tests, the founder switch, the config keys and the
attempt cap all worked; what failed was state that did not survive a restart, and claims the change made about
itself that nothing checked.

### F1 — the founder's decision did not outlive the process that heard it (blocking)

`conductor on --founder` set `options.ConductorEnabled` in memory. After `muthur down && muthur up` the conductor
was silently off, with `conductor.on` still standing in the ledger as the last founder decision.

`docs/PLAN.md` §1 states the rule this broke: every piece of state is in the database, nothing in memory that
matters. The hub is a local process that is off for hours — this is exactly the state that had to be persisted.

The switch is now a `MetaEntry` (`conductor_enabled`), read on every pass and by `status`. `Muthur:ConductorEnabled`
becomes the *starting* value for a hub that has never been told either way. Pinned by
`The_founders_decision_outlives_the_process_that_heard_it`, which brings a second hub up over the same database.

### F2 — the config table named two settings that do not exist

`` `Muthur:ConductorMaxSessions` / `SessionMinutes` / `MaxAttempts` `` reads, by the convention of the row above it,
as three complete keys. Two of them are inert. Each key is now written out in full, and
`Muthur:ConductorIntervalSeconds` — real, and missing from the table — has its own row.

### F3 — the spec promised a `status` that was not built

The spec said "what it has running, **and what it last did**". `ConductorStatusDto` reported neither. It now carries
`IntervalSeconds`, `LastPass` and `LastAction`, because a founder who turned this on overnight needs to know it ran
at all — "enabled, 0 running" reads the same whether it is working or wedged.

### F4 — two bullets of this spec's own Verification section had no test

Both are now covered, and the second one was worth the failure:

- The attempt cap had none. `After_three_failed_verdicts_it_stops_and_asks_the_founder` drives three real failed
  verdicts and asserts `conductor.exhausted` with no `conductor.staffing`.
- `Whoever_built_it_is_the_harness_the_validator_avoids` asserted `AvoidHarness is null or { Length: > 0 }` — true
  of every value but the empty string. It tested nothing. The preference is now exercised directly:
  `ValidatorSessionLauncher.Prefer` is `internal`, and a theory covers claude→codex, codex→claude, no preference,
  and the case the spec named and the old test missed — when the other vendor is out of quota, the builder's own
  harness validates rather than nothing validating.

The spec also said the escalation raises a *founder request*. It cannot: `RequestService.AskAsync` requires an agent
caller and the conductor is the hub itself. It posts a founder message instead, which now carries the failed
verdicts rather than only their count. The spec is corrected here rather than the code bent to match it.

Not addressed, by the validator's own reading: `docs/PLAN.md` gains nothing for the conductor. That belongs to T-9,
which exists to refresh the plan in one sweep, and doing it here would collide with it.
