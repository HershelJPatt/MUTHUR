# T-11 — The conductor staffs validation, so a passing task needs nobody

> Scoped deliberately to **validators only**. That is the half that removes the founder from the loop for every
> task that passes, and the half with an unambiguous success condition: a task reaches `validating` while nobody
> is watching, and is `validated` or failed-with-evidence by morning.

## Why this is not `muthur worker run`

`WorkerLauncher` (`src/Muthur.Launch/WorkerLauncher.cs:20`) scrubs `MUTHUR_AGENT` and `MUTHUR_TOKEN`:

> Hub identity never reaches a worker: workers have no authority in the organization.

That rule is correct and this task must not weaken it. A worker implements a frozen spec in a worktree and reports
to its orchestrator; it cannot claim, land, or vote. A **validator is the opposite**: it holds a role, reads a
task, and casts a verdict that decides whether work ships. It needs identity.

So there are two kinds of launched session, and the difference is authority. This task names that difference in
code rather than leaving it implicit in one launcher that does both.

## Design

### `AgentLauncher` — a session that acts *as* somebody

A sibling of `WorkerLauncher` in `Muthur.Launch`, sharing the adapters and the candidate/rate-limit logic:

| | `WorkerLauncher` | `AgentLauncher` |
|---|---|---|
| `MUTHUR_AGENT` / `MUTHUR_TOKEN` | scrubbed | **set** |
| `muthur` commands | denied | allowed |
| Working directory | a worktree made for it | the project's repository root |
| Worktrees | given one | makes its own, as the validate procedure says |
| Reports by | printing to its launcher | calling the hub itself |

The agent it acts as is registered by the conductor, with its own token, exactly as a human-started session would
be. Nothing about a conductor-started validator is privileged over one the founder starts in a terminal.

### `ConductorService`

A `BackgroundService` beside `IngestWorker`. Each pass, inside one `Ledger.ReadAsync`:

1. Tasks in `validating`.
2. For each, the required validator roles with no `yes` yet **and no live holder**.
3. Skip any task that is `blocked`, and any role already held — the hub's leases refuse a second holder, and the
   conductor must not use that refusal as flow control.
4. Up to the remaining concurrency budget, launch one validator session per (task, role).

The bounce-back loop needs no new states: a failed task is already back with its owner, and if that session has
exited its claim lapses, so the task is unclaimed and staffable again. **The conductor adds no state to the
machine it serves.**

### Choosing who validates

From the tier catalog, `mastermind` candidates whose account is not limited. Prefer a candidate whose **harness
differs from the one that built the task** — read from the `task.implemented` event's `actorModel`. The same idea
as `RequireCrossProviderReview` in the outbound gate, applied to validation: Codex checks what Claude wrote.

Preference, not a rule. If the only candidate left is the same harness, validating is better than not.

### What the founder controls

```
muthur conductor status              # on/off, budget, what it has running, what it last did
muthur conductor on | off --founder  # recorded in the ledger like any other founder decision
```

`Muthur:ConductorEnabled` (default **false** — it does not start staffing because someone upgraded),
`Muthur:ConductorMaxSessions` (default 2), `Muthur:ConductorSessionMinutes` (default 45).

The founder has said unattended spending is allowed, so there is no separate night budget. `agent limited` is
still respected: a limited account leaves the rotation, and if no candidate remains the conductor stops rather
than degrading to a tier it was not asked for.

### Not looping forever

A task whose validation fails is restaffed on the next pass. Left alone that is a crash loop, spending a
subscription all night on the same failure.

Count `validation.failed` events per task. At **three**, the conductor stops staffing it and raises a founder
request naming the task and the three verdicts. A repeated failure is a judgment call, and judgment calls go to
the founder — which is the same rule the rest of this system already follows.

## Out of scope

Staffing **orchestrators**. Today the founder's `/loop` is what starts an orchestrator, and that works; adding a
second mechanism before validators are proven would make two things unproven instead of one. Nested fleets (T-19).
Any change to `worker run` (T-15).

## Verification

```
dotnet build && dotnet test
```

New tests in `Muthur.Server.Tests` against the real HTTP API through `HubFactory`, with a fake launcher recording
what it was asked to start:

- a task in `validating` with an unheld required role → one launch, for that task and role;
- the same task with the role **held by a live agent** → no launch;
- a `blocked` task → no launch;
- two tasks and `ConductorMaxSessions=1` → one launch, not two;
- a task whose `implemented` event names `claude` → the chosen candidate is `codex` when both are available, and
  `claude` when Codex's account is limited;
- three `validation.failed` events on a task → no further launch, and a founder request exists naming it;
- `ConductorEnabled=false` → no launches at all;
- `conductor off` by the founder is in the ledger and takes effect on the next pass.

Unit tests in `Muthur.Launch.Tests` for `AgentLauncher`: the environment it builds **contains** `MUTHUR_AGENT` and
`MUTHUR_TOKEN` (the inverse of the worker case, which is asserted alongside it so the two can never quietly
converge), and `muthur` is in the allow list rather than the deny list.

End to end, against a scratch hub with a real repository and `ConductorEnabled=true`:

1. Drive a task to `validating` with a required validator role that nobody holds. Without touching anything else,
   a validator session starts, takes the role, and the task reaches `validated` or fails with evidence.
2. Kill the validator session mid-run; the role lease lapses and the next pass restaffs it.
3. `conductor off`, drive another task to `validating`, confirm nothing starts.

## Round 2 — what validation found

`docs-validator` failed round 1 with four defects. Build, tests, the founder switch, the config keys and the
attempt cap all worked; what failed was state that did not survive a restart, and claims the change made about
itself that nothing checked.

### F1 — the founder's decision did not outlive the process that heard it (blocking)

`conductor on --founder` set `options.ConductorEnabled` in memory. After `muthur down && muthur up` the conductor
was silently off, with `conductor.on` still standing in the ledger as the last founder decision.

`docs/PLAN.md` §1 states the rule this broke: every piece of state is in the database, nothing in memory that
matters. The hub is a local process that is off for hours — this is exactly the state that had to be persisted.

The switch is now a `MetaEntry` (`conductor_enabled`), read on every pass and by `status`. `Muthur:ConductorEnabled`
becomes the *starting* value for a hub that has never been told either way. Pinned by
`The_founders_decision_outlives_the_process_that_heard_it`, which brings a second hub up over the same database.

### F2 — the config table named two settings that do not exist

`` `Muthur:ConductorMaxSessions` / `SessionMinutes` / `MaxAttempts` `` reads, by the convention of the row above it,
as three complete keys. Two of them are inert. Each key is now written out in full, and
`Muthur:ConductorIntervalSeconds` — real, and missing from the table — has its own row.

### F3 — the spec promised a `status` that was not built

The spec said "what it has running, **and what it last did**". `ConductorStatusDto` reported neither. It now carries
`IntervalSeconds`, `LastPass` and `LastAction`, because a founder who turned this on overnight needs to know it ran
at all — "enabled, 0 running" reads the same whether it is working or wedged.

### F4 — two bullets of this spec's own Verification section had no test

Both are now covered, and the second one was worth the failure:

- The attempt cap had none. `After_three_failed_verdicts_it_stops_and_asks_the_founder` drives three real failed
  verdicts and asserts `conductor.exhausted` with no `conductor.staffing`.
- `Whoever_built_it_is_the_harness_the_validator_avoids` asserted `AvoidHarness is null or { Length: > 0 }` — true
  of every value but the empty string. It tested nothing. The preference is now exercised directly:
  `ValidatorSessionLauncher.Prefer` is `internal`, and a theory covers claude→codex, codex→claude, no preference,
  and the case the spec named and the old test missed — when the other vendor is out of quota, the builder's own
  harness validates rather than nothing validating.

The spec also said the escalation raises a *founder request*. It cannot: `RequestService.AskAsync` requires an agent
caller and the conductor is the hub itself. It posts a founder message instead, which now carries the failed
verdicts rather than only their count. The spec is corrected here rather than the code bent to match it.

Not addressed, by the validator's own reading: `docs/PLAN.md` gains nothing for the conductor. That belongs to T-9,
which exists to refresh the plan in one sweep, and doing it here would collide with it.

## Round 3 — three defects, all introduced by round 2

Round 1's four findings were confirmed fixed. These were new, and all three came from the fixes themselves.

### G1 — `DateTimeOffset.UtcNow` in server code (blocking)

`_lastPass = DateTimeOffset.UtcNow` broke the rule `CLAUDE.md` states outright: time comes from the injected
`TimeProvider`, never `DateTimeOffset.UtcNow`, in server and core code. It was the only instance in the tree
outside `FileLogger`, and the clock was already at hand twice over.

The cost was not cosmetic, which is the part worth keeping: `HubFactory` runs on a `FakeTimeProvider` pinned to
2026-01-01, so a wall-clock timestamp can never be asserted by a server test — which is exactly why neither new
field had one. `ConductorService` takes `TimeProvider` again, and `What_it_last_did_is_on_the_injected_clock`
asserts `LastPass` equals the fake clock's now.

### G2 — a session that could not start was retried forever

The spec's own risk list said "respect `agent limited`, and **stop rather than degrade**". It respected the limit
and then never stopped: with every account limited, `StartAsync` threw before launching anything, the key was
released in `finally`, and the next pass staffed the same pair again — once per interval, all night, ~2,880 ledger
events for a hub that validated nothing, while `status` read perfectly healthy.

The attempt cap was designed for repeated *validation* failure and had no equivalent for repeated *launch* failure.
It does now: consecutive launch failures are counted per task and role, the pair is skipped once it reaches
`ConductorMaxAttempts`, and the founder gets one message saying what stopped it. A launch that succeeds clears the
count, so a harness that comes back is picked up again without intervention.

The counter is deliberately **not** persisted, unlike F1's switch. A restart is a deliberate act that usually
changes the conditions that were failing — the Discord token was fixed exactly that way — so three fresh attempts
after a restart is the correct behaviour, not the bug F1 was.

### G3 — the founder's notification was 13.7 KB of escaped JSON

Round 2 made the escalation "carry the failed verdicts". It pasted `e.PayloadJson` — the whole event payload,
evidence and all. Measured at 13,734 characters for three ordinary verdicts, on one line, on a card.

`FirstLineOfEvidence` now parses the payload and takes the first non-empty line of `evidence`, capped at 140
characters, with the verdict's date and validator. The message ends with `muthur task show T-n`, where the evidence
is whole and belongs. Measured after the fix: **152 characters**. Covered by a theory including malformed JSON, a
missing field, a null field, and a 4,000-character verdict.

### Not T-11's, but found while fixing it

`tests/Muthur.Server.Tests` is flaky under parallel load. On this branch a full run failed
`MessagingTests.A_waiting_inbox_ends_the_moment_the_hub_stops`; on **main**, unchanged, a full run failed
`OutboundTests.Bytes_changed_after_review_are_not_sent`. Both pass in isolation and on a re-run. This branch raises
the server suite from 98 tests to 122 and so surfaces it more often, but it does not cause it. Filed separately.

## Round 4 — the stall had no way back

Round 3's three findings were confirmed fixed. One new finding, in the round-3 fix itself.

### H1 — once stalled, a pair never recovered without a restart, and the spec claimed it did

Round 3's spec said "a launch that succeeds clears the count, so a harness that comes back is picked up again
without intervention". That was true only *before* the cap — the state where it does not matter. After the cap
`PlanAsync` skipped the pair, so `StartAsync` was never called again, so the line that cleared the count was
unreachable. The validator cleared both account limits, waited six intervals, cycled `conductor off`/`on`, and
nothing moved; only a restart resumed it.

So round 3 stopped the hub from spinning and put a permanent stop in its place — the same silent wedge one step
later, and the founder was told what stopped but not what to do.

The stall is **half-open** now. After `ConductorMaxAttempts`, one probe is let through every
`ConductorStallProbeMinutes` (default 30). A probe that starts clears the count; one that fails re-arms the cooldown
and says nothing further, so the founder is told once rather than every half hour. `conductor on` also clears every
stall, because turning it on is the founder saying "try now". The restart behaviour round 3 argued for is unchanged.

The stall message now names both ways back.

### H2 — found by the probe, not by the validator

With the quota cleared, the probe got past the candidate check and hit a defect one layer down:

```
attempt 4: Both --harness and --model are required: the ledger records which model did what.
```

`ValidatorSessionLauncher` registered its agent from `candidates[0]`, and a tier entry may legitimately leave the
model blank to mean "the harness's own default" — `codex` does exactly that in the shipped catalog. So the very
first fall-through to Codex would have failed to register, and this is the cross-provider path the README sells.

Registering from `candidates[0]` was wrong for a second reason: `AgentLauncher` falls through to another candidate
when an account is out of quota, so the session's ledger entries would have named a vendor that did not run.

`AgentLauncher.RunAsync` now takes `Func<HarnessCandidate, Task<AgentIdentity>>` rather than a fixed identity, and
registers for the candidate about to run. A blank model registers as `default`, the word `worker run` already uses.
Covered by a theory over both cases.

## Round 5 — the door round 4 said was closed

Round 4's two findings were confirmed fixed. One new finding, and it is the round-2 defect reached another way.

### I1 — an unrunnable harness was a silent success

`AgentLauncher` does not throw for a harness the build does not know, or a CLI that is not on the hub's PATH. It
records the reason as an *attempt* and returns normally:

```csharp
if (Harnesses.Find(candidate.Harness) is not { } adapter) { attempts.Add(…); continue; }
if (_resolve(invocation.FileName) is not { } executable) { attempts.Add(…); continue; }
```

`StartAsync` never looked at `attempts`. So `RunSessionAsync` took the success path, cleared the stall counter,
recorded no `conductor.failed`, and the next pass staffed the same pair again — the counter could never reach
`ConductorMaxAttempts`, so the half-open stall built in round 4 never armed. Measured by the validator: six
staffing events in ninety seconds, not one failure, `status` reading perfectly healthy.

The hole had been there since round 1. What made it round 4's to fail is the README sentence added that round,
which named "a harness missing" as one of the cases the three-strikes path covers.

`EnsureSomethingRan` now throws when no attempt succeeded, carrying the last attempt's own message, so everything
meaning "no session ran" leaves by the same door as "no candidate at all". A session that *ran* and voted no is not
a launch failure — that is the system working — and there is a test saying so, because that distinction is the
whole point of the check.

Also this round, both from the validator's notes: the stall message said "1 minutes"; and `conductor status` now
reports `stallProbeMinutes`, which was the one number a founder waiting on a probe could not see.

## Round 6 — the other half of round 5

Round 5's finding is fixed, and the validator exercised E2E item 1 for the first time in five rounds with a
stand-in harness: a task reached `validating` with nobody awake, the conductor registered an agent, handed it
`MUTHUR_AGENT` and a token, started it in the project's repository, and the task came out `validated`. That is the
whole promise of this task, working.

### J1 — a session that ran until it was reaped was reported as one that never started

Round 5 keyed `EnsureSomethingRan` on `Outcome.Success`. That is not "a session ran": for `ClaudeAdapter` it is
`!is_error && result.Ok`, and a session killed at `ConductorSessionMinutes` has `result.Ok == false`. So a validator
that started, took the role and worked until the timeout reaped it came back through the *launch-failure* door, and
the founder was told the conductor "could not start a validator" — sent looking for a missing CLI when the fault was
hanging sessions. The one identifier in the message was `cmd.exe`, the npm shim wrapper, not even the harness.

Round 5 stated the right rule in its own test comment and did not implement it. The test could not catch the gap: it
is a unit over hand-built attempts, so it only ever saw the `Success` flag it was handed.

Whether a process was reached is knowable and is not `Success`. `WorkerAttempt` carries `Started`, false only for the
two cases that never reach one — an unknown harness, or a CLI not on PATH. `EnsureSomethingRan` now throws
`ValidatorLaunchException` when nothing started and `ValidatorSessionException` when something did, and the conductor
records `conductor.failed` or `conductor.session_failed` accordingly, with the message and `lastAction` to match.

Both still feed the same attempt cap, because the founder-facing consequence is the same — this pair is not
progressing and the subscription should stop being spent on it. Only the wording differs, and the wording is the
whole point: it is what tells the founder where to look.
