## Design
### Classification and evidence
Recognize one optional standalone `work-kind: mechanical|complex-debugging|ui-interaction|general` line in a committed frozen spec. Missing means unknown; duplicate conflicting or unrecognized values fail with invalid_work_kind. Preserve explicit capabilities, including platform requirements, as independent constraints. Do not infer platform/tool eligibility from category. Existing specs and launches remain compatible. Append optional WorkKind and PolicyVersion fields to WorkerRunReport and WorkerRunDto; preserve them in worker events/receipts. Legacy records stay unknown. Default worker launches record catalog-order-v1 and parse classification from their pinned spec; no ordering change.

Use exact candidate identity (tier, harness, model, account, reasoning effort when observed) and work kind; history without sufficient identity is unattributed, not silently joined. Receipts retain run IDs, revision/spec provenance, missing resource values and timestamps. Extend optional metadata only where available from existing launch observations: Started and per-attempt evidence must distinguish pass-over from actual process starts. Never count registrations as OS starts, or conflate final reports with all attempts. Preserve each failed/rate-limited attempt in the existing worker ledger seam with its run ID; deduplicate by run ID when present. Unknown historical start counts remain null.

Expose historical reported success separately from independently established product completion. Validation failures/rework and false approvals are distinct: absent an external correctness observation, false approvals are unknown. Do not attribute a task's aggregate validation outcomes to one worker if multiple runs contributed. TaskStateTimeline supplies clipped task phase durations, dependency wait, validation time, age and completion windows. Distinguish task-state duration from actual model execution duration. Return evidence references (ledger sequence/run/task IDs) and explicit missing-data reasons.

### Report surface
Add `muthur routing report --task T-n --spec <path> --base <ref> --default-branch <name> [--tier implementer] [--hours 168]`. Resolve immutable spec/base as WorkerAssignment does. Hours range 1..720. No model calls, probes, worktrees or task mutations. Read catalog, existing receipts/task evidence and conductor status; inspect capability evidence for each candidate through CapabilityEvaluator using the same effective request inputs as WorkerCommands. Unknown required capabilities exclude a candidate before ranking. Empty requirements explicitly say legacy unchecked, not demonstrated. Unsupported conductor/native identity inspection stays unknown; never borrow worker-run observations.

Return JSON schemaVersion=1, policyVersion=measured-quality-v1, generatedAt, ledger sequence boundary, window, exact task/spec/base identities, work kind, capability requirements, prior catalog order, recommendation, rationale and candidate evidence. Candidate eligibility and availability are separate: retain quota-limited entries and their suitability evidence, but never recommend them for immediate staffing. Show current capacity/daily admission as required gates; a report is never a reservation or permission to launch. Required reviewer independence must be satisfied by the existing validator route; first slice only recommends implementers, rejecting other tiers with routing_tier_unsupported.

Ranking: filter capability-ineligible candidates, then unavailable candidates from actionable recommendation. Fewer than five comparable independently observed outcomes is unknown quality. Unknown or incomparable quality means deterministic catalog-order fallback, with the reason visible. Among candidates with comparable observed quality, order by lower false-approval rate, higher independent successful outcomes per observed actual start, fewer rework outcomes per sample, lower observed end-to-end time; ties use original catalog position. Missing any required ranking dimension prevents a quality-based reorder. Do not rank on price/tokens or conflate synthetic benchmark history with real history. This intentionally often falls back on the current ledger.

Read queue context without staffing: dependencies not done are excluded; explicit priority is primary, age then task ID breaks ties. Report oldest ready task and pending validation demand. Measured comparison reserves one of its two simulated slots for pending eligible validation and does not admit lower-priority work ahead of higher-priority ready work; same-priority FIFO prevents starvation. This advisory queue order never mutates conductor scheduling.

### Durable reconstruction
Add an explicit `muthur routing record` command with the same inputs. This records the exact report snapshot as one routing.recommended event for the owned in-progress task, through a new identified-owner-only server endpoint. Bound snapshot to 256 KiB; reject malformed/unknown policy/schema, wrong task, invalid window and oversized input. Store client-generated capability observations as observations with provenance, not server-certified authorization. Server attaches actor, time and sequence; no user-supplied ownership. `muthur routing show --task T-n` reads persisted snapshots in sequence order. Restart reconstruction displays recorded inputs/reasons unchanged; later catalog/history changes do not rewrite history. Report GET/read alone writes nothing. No default policy setter in this slice; rollback is simply continuing catalog-order-v1, with no task requeue/restaff operation.

### Deterministic comparison and real cohort contract
Add routing fixtures to the T-102 organizational benchmark, using the production pure ranking function and fake clock/launch observations. Both policies receive identical eligible candidates, workload, seedless scripted outcomes and two simulated slots. Cases cover capability exclusion despite cheap/successful history, sparse history, quota wait vs model failure, independent false-green detection, validation pressure, dependency readiness, high-priority FIFO, restart replay and fallback/rollback without duplicate starts. Use the existing external result grader for product correctness. Wrong output with reported success is not product completion.

Add scripts/benchmark-routing.ps1 taking -BaselinePolicy catalog-order-v1 -CandidatePolicy measured-quality-v1 -Output <new directory> [-Trials 1..10]. Capture resolved product/driver revisions, fixture hash/version, cohort, UTC window, sample count, actual host duration separately from fake elapsed, staffing attempts, simulated starts, actual OS starts (zero model starts), worker outcomes, independent correctness, waits, validation queue, rework, oldest-ready age and resource missingness. Bound simulated concurrency to two. Deterministic fixture results cannot populate real routing history or claim model benefit. Nonzero/missing/incompatible evidence fails the command. Follow T-102 owned-child cleanup and output-directory rules.

Match comparable tasks before interpreting results; never retry to fill the sample, include failed starts/waits and report incomplete windows. No automatic activation or promotion. Stable independent correctness and a measured non-resource outcome improvement are necessary for later promotion; small uncontrolled samples are descriptive only.
