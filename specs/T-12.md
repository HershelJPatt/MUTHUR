# T-12 — The kit is installed into MUTHUR itself, and the brief that gates it is true

> The last task the founder validates by hand. After it lands, the conductor holds a real validator role with a
> brief worth handing an agent, and it validates everything after it.

## What is wrong today

T-2 shipped four starter briefs and made `kit install` write them. This repository — the one MUTHUR was built in,
and the only project it serves — never had them installed. Its gate is `docs-validator`, a brief written by hand
in an afternoon to unblock T-1, describing how to validate **documentation**. T-4, T-11 and everything since were
code, and each was judged against a job description that does not cover them.

`.claude/skills/muthur-orchestrate` and `muthur-validate` were also stale, last written before T-2 and T-4 landed.

## Design

`muthur kit install --harness claude` writes the four starter briefs to `briefs/` and refreshes the procedures.
`briefs/docs-validator.md` is left alone: `mode: create` does not touch a brief that exists, which is the guarantee
T-2 was built around, and this is the first time anything has depended on it.

### `briefs/validator.md` becomes this project's real validator brief

The starter's `TODO(founder)` sections are filled in with what is true here. Almost none of it is new writing:
`kit/briefs/muthur-win-validator.md` already holds six validation rounds' worth of hard-won specifics — the two-hub
separation, never exporting `MUTHUR_HOME`, always passing `-Destination`, running only an installed CLI, the
per-run scratch directory, the cleanup proof.

That file is **deleted** in the same commit. Two briefs describing one job is the drift this task exists to end,
and the naming convention T-2 set says `kit/briefs/<role>.md` is a starter shipped to other repositories while a
real brief belongs in the project it serves. Past specs reference it by path; they are a record of what was true
when they were written and are left alone.

Three traps this organization learned the hard way go in, because each cost an agent real time and each currently
lives only in an evidence file:

- Bare `Invoke-RestMethod` against Discord's API is refused without a `User-Agent`. The hub is unaffected; do not
  read that 403 as a bad token. (T-4)
- A hub started from a shell opened before an environment variable was set comes up blind to it, silently. (T-4)
- A stand-in harness on PATH exercises the whole launch path without spending the founder's subscription — but
  `timeout /t` refuses redirected stdin and exits at once, so a shim built on it reports a clean success rather
  than a hang. Use `ping -n`. (T-11)

### The roster

`validator`, `comms-oncall`, `observability-oncall` and `release-oncall` are defined from their briefs, and the
`muthur` project requires `validator` in place of `docs-validator`. `docs-validator` is not deleted — it is a real
role with a real brief, correct for documentation-only tasks, and the founder may still require it.

## Out of scope

Filling in the three on-call briefs beyond what ships: nobody holds those roles yet, and a brief written for a job
nobody is doing is the thing this task is fixing. `docs/PLAN.md` (T-9).

## Verification

```
dotnet build && dotnet test
```

- `muthur kit install --harness claude` is idempotent here: a second run reports every brief `kept` and the
  procedures `unchanged`, and `briefs/docs-validator.md` is byte-identical throughout.
- `briefs/validator.md` contains no `TODO(founder)`.
- `grep -rn "muthur-win-validator" --include=*.cs --include=*.json src kit` finds nothing — no manifest or code
  referenced it, which is why deleting it is safe.

Against a scratch hub with its own `MUTHUR_HOME`/`MUTHUR_URL` and an installed CLI under `artifacts/`:

1. Define the four roles from the printed commands; `role list` shows `validator` with `isValidator: true` and the
   three on-calls with `false`.
2. `role brief validator` returns the filled-in brief from the hub, with no `TODO(founder)` in it.
3. A task driven to `validating` on a project requiring `validator` waits on that role, and a verdict from an agent
   holding it moves the task to `validated`.

## Round 2 — what validation found

Every item of the *Verification* section above passed, and the validator went well past it: the four `define`
commands, the gate's refusals (`role_not_held`, `validator_not_required`, `self_validation`, `role_held`), every
exit code the brief claims, CLI latency, the log, and the `kept` guarantee proved by deleting the brief and watching
the starter come back with its five `TODO(founder)` markers.

Two defects, both in `briefs/validator.md`, which is this task's whole deliverable.

### D1 — the brief's only executable proof of the lease behaviour could not run (blocking)

The race snippet used `$X`, defined nowhere. Run as written it produces `env: 'task': No such file or directory`,
exit 127 — hidden by the snippet's own `>/dev/null 2>&1`. The line above it says "Races are how the leases are
proven", and the comment promises `# exactly one 0, one 3`, which nobody had ever seen.

It was inherited verbatim from `kit/briefs/muthur-win-validator.md`, **which this commit deletes** — so this was the
last chance to catch it, and it survived six validation rounds there.

The brief now defines `M=./artifacts/validate/muthur.exe` beside `T` and uses `env $T $M` in all three blocks, so
there is one spelling of the CLI path and no undefined variable anywhere.

> **This paragraph originally claimed the fix was "verified by running every command block in the brief verbatim …
> `project add`, two `agent register`, `task add`, and the race". That claim was false and round 3 caught it.** The
> brief contained one `agent register`; the second was typed by hand at the terminal and never existed in the
> document. The commands run were not the brief's commands. Left here rather than quietly deleted, because a spec
> that edits away its own false claims is worth nothing to the next reader.

The root cause is worth naming, because it is the one thing a brief cannot survive: the block was written by copying
and was never executed. The brief now says so in its own text — run every command block rather than reading it and
agreeing — which is the same instruction it gives about diffs, applied to itself.

### D2 — the suite's duration was wrong in the direction that matters

"about 30 seconds" against 71 s measured twice by the validator and 59 s here. A validator who reads 30 and then
watches the server suite sit silently for a minute has been told to expect a hang that is not one. Now: "a minute or
so (59-71s observed) — nearly all of it the server suite", with a line saying the silence is normal.

Unlike D1 this was new writing in this commit; the deleted brief said only `dotnet test   # all green`.

### Re-verification

`dotnet build` 0 warnings · `dotnet test` 3859 pass, 59 s wall. Every bash block in `briefs/validator.md` executed
verbatim, including the race. No undefined variable remains in any block.

## Round 3 — the same two lines, a third time

Everything in *Verification* passed again, and the validator went well past it: the gate exercised and attacked
(`role_not_held`, `validator_not_required`, `self_validation`, `role_held`, `not_validating`, `branch_missing`),
exit codes 0/2/3/4/5/6 all observed, 80 ms `status`, a clean scratch log, `kit install` idempotent with
`docs-validator.md` byte-identical throughout, and the hub's copy of the brief identical to the file on both the
scratch and the live hub.

### L1 — `a2` was never registered anywhere in the brief (blocking)

The race block claims `# exactly one 0, one 3`. Run the brief's blocks in order and it gives `a1=0`, `a2=6`
(`unauthorized`) — because the setup block registers only `a1`. The block's own `>/dev/null 2>&1` hid the reason,
exactly as it hid `$X` in round 1. Same two lines, same hiding mechanism, third round.

Fixed in `979d5ce`, which went further than the report required: the setup block gains `a2` **and** the `env $T $M`
prefix it was missing, and the same omission is corrected on the `role define`, `project set` and `down` commands in
the surrounding prose — every command in the brief now names the build under test.

### The verification method, which is the actual defect behind all three rounds

Rounds 1 and 2 both failed on the same block for the same reason: the blocks were **retyped** at a terminal rather
than taken from the document. Retyping is how a missing variable, and then a missing agent, kept passing — the
person running them supplied what the document lacked, without noticing they were supplying anything.

The blocks are now extracted from the markdown and executed, so nothing can be supplied by hand:

```bash
python -c "import io,re; s=io.open('briefs/validator.md',encoding='utf-8').read(); \
  print('\n'.join(re.findall(r'\`\`\`bash\n(.*?)\`\`\`', s, re.S)))" > blocks.sh && bash blocks.sh
```

Run that way against a fresh scratch hub, with nothing typed by hand: `status` → exit 4 with the documented
message; `up`; the setup block registers `a1` and `a2` and adds the task; the race → **`a1=0`, `a2=3`**.

### Re-verification

`dotnet build` 0 warnings · `dotnet test` 3859 pass. Every bash block in `briefs/validator.md` extracted from the
file and executed; no undefined variable and no unregistered identity remains in any of them.

### Recorded because it happened

While verifying this round the owner ran `muthur down` without a `MUTHUR_HOME`/`MUTHUR_URL` prefix and stopped the
**live** hub — the mistake this very brief warns about in bold, made by the person who wrote the warning. The hub
was restarted and nothing was lost, because every piece of state is in the database. Two things worth taking from
it: the warning is warranted, and the fact that it cost nothing is the §9 rule earning its keep.
