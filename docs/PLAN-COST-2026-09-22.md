# Context, token and friction plan — 2026-09-22

Status: proposed · evidence from the live ledger (92 landed tasks, 7,622 events, 09-17 to 09-21), the kit sizes,
and `muthur sim run` at fbf2182 · pi harness deferred to Phase 5

## 0. What the evidence says

Per landed task on the live hub: 6.7 conductor staffings, 3.3 sessions that ran and produced nothing, 1.9 orchestrator
claims, 0.75 validation fail/blocked rounds, 4.1 worker runs, median 2.3 h claim-to-done. 37 of 92 tasks landed with one
claim and no bounce. The waste, in order of size:

| # | Waste | Evidence | Root cause |
|---|---|---|---|
| 1 | Launches into a rate-limited account | 376 of 399 failed sessions are Codex "You've hit your usage limit", about one per pass for 6 h on 09-19; 27 more after the 09-20 quota fix | account limit not applied on the conductor path; no test, and the sim has no limited candidate |
| 2 | Implementer runs that do not finish | 107 Codex implementer runs: 17 done, 24 blocked, 14 spec-problem, 9 timeout, 28 crashed; 13.7 worker-hours for 17 done units | (a) sandbox user cannot read `NuGet.Config` or write `.git/worktrees/*`, about half of blocked; (b) prompts with an abbreviated SHA or no named base, about a third; (c) the 13 KB contract re-runs a git ritual the launcher already ran |
| 3 | Validator sessions duplicating integration | one agentic validator per task rebuilds and retests; integration then rebuilds and retests deterministically; 19 verdicts were `blocked` on environment | no checks-only path; `RequiredChecks` is on the subject but only integration uses it |
| 4 | Unmeasured context and cost | `costUsd` is 0 in all 534 worker events; conductor sessions never record cost; Codex prints `tokens used` and nothing parses it; sim `promptBytes` counts the launcher prompt only; the T-67 probe put the floor at $0.31 / 34 s for `hello.txt` | outcomes are logged, not recorded |
| 5 | Timeouts with nothing to show | 17 sessions hit 45 min and left no notes | notes only on the question-wait path; `timeout` failure kind derived then dropped |
| 6 | Resume cold starts | 44% of tasks asked a question; median answer 16 min, p75 67 min | in-session wait covers about half |
| 7 | Unread messages | 255 of 598 never read; 129 "ready for validation" posts to `role:validator` nobody polls | hub posts to a role the conductor already staffs |
| 8 | Effort and tier are static | `reasoningEffort` is a catalog constant; routing always falls back to catalog order because the CLI reports 0 comparable outcomes; the only bound on a session is wall clock | routing built but never fed |

The sim (54 s, 2.33 cold starts per landed task today) is a scheduler test: `modelCalls` is a literal 0, no worker
runs, no build, no rate limit, and `SimSession.Parse` rejects an implementer prompt. Rows 1, 2 and 4 are invisible to it.

## 1. Rules for this work

- Dogfooding stays paused; work directly on `main`, one branch per phase, one commit per unit, tests beside the
  classes named below. Each phase ends with the sim re-run and its numbers appended to §7.
- Nothing in Contracts/Core/Data/Server names a vendor; token parsing lives in `Muthur.Launch` adapters.
- Every new decision the hub makes on a session's behalf (a deterministic verdict, a refused dispatch, a skipped
  launch) is a ledger event with a stable code. Silence is the failure mode this repo has already paid for.
- Nothing here changes what counts as validated: a checks-only verdict is opt-in per project and only for specs that
  declare no judgment check.

## 3. Phase 1 — Stop the deterministic waste at the launcher

### U1.1 Rate-limit guard with backoff
- **Files:** `HarnessService.ExhaustedAsync` (repeat exhaustion within the window doubles the limit: 1 h, 2 h, 4 h, cap 8 h;
  `account.limited` payload carries `attempt`), `ConductorService` (a candidate list emptied by limits records
  `conductor.skipped { role, reason: "accounts_limited", until }` once per task per window, not once per pass).
- **Acceptance:** `ConductorTests`: a fake launcher that reports rate-limited on every start is launched at most once
  per account per hour across 200 fake passes; `sim run` shows `launchesIntoLimitedAccount` = 1.

### U1.2 Worker environment preflight
- **Files:** new `src/Muthur.Launch/WorkerEnvironment.cs`; `WorkerCommands.RunAsync` between the spec parse (line ~255)
  and admission; `muthur doctor` gains the same checks.
- **Does:** before any reservation, for the candidate harness, verify deterministically what the 09-21 blocked reports
  named: the worktree's git common dir is writable by the launching identity, `NuGet.Config` and the package cache are
  readable, `TEMP` is writable, `dotnet --version` runs. For Codex this runs under the sandbox identity the adapter will
  use (the probe engine in `CapabilityEvaluator` already knows how to derive it); the result is cached per
  (harness, machine, day) under `MUTHUR_HOME/capabilities` like an observation. A failure refuses with
  `worker_environment_unavailable` naming the path and the identity, records `worker.failed { failureKind: environment }`,
  and starts no model.
- **Investigation result (2026-09-22):** Codex's Windows sandbox (`[windows] sandbox = "elevated"`) runs workers as
  the local users `CodexSandboxOffline`/`CodexSandboxOnline`, both members of the local group `CodexSandboxUsers`.
  Codex itself grants that group read on `%USERPROFILE%\.nuget\packages` and modify on the workspace, but
  `%APPDATA%\NuGet` and `NuGet.Config` carry only SYSTEM, Administrators and the user, so every `dotnet restore`
  in the sandbox fails before compiling. The `.git` directory carries explicit deny entries for the sandbox users
  (Codex's own "keep .git read-only" rule), which is the `ORIG_HEAD.lock` refusal; the launcher already commits
  on the worker's behalf for that case. The fix is a one-time ACL grant, which the preflight prints and `muthur
  doctor` repeats: `icacls "%APPDATA%\NuGet" /grant "CodexSandboxUsers:(OI)(CI)(RX)"`. Built as `WorkerEnvironment`
  (an ACL read, no cache needed at that cost) and applied in `worker run` before admission and in the doctor.
- **Acceptance:** `Muthur.Launch.Tests/WorkerEnvironmentTests` with a fake process runner; `WorkerAdmissionTests`:
  a failing preflight reserves no seat.

### U1.3 The assignment is verified once, by the launcher
- **Files:** `kit/core/implementer.md` split into `implementer.md` (assignment, how to work, boundaries, report;
  target under 4 KB) and `kit/core/implementer-recovery.md` (the ancestry and reset ritual); `WorkerPrompt.Compose`
  inlines only the short contract plus a "verified by the launcher" block (named base, full SHA, default branch,
  spec blob, worktree, output branch, verify commands) and the two re-checks a worker still owns: base still equals
  the SHA, tree clean; `kit/claude/agents/muthur-implementer.md` (native isolation, where worktrees do arrive on the
  wrong branch) keeps the recovery file by reference; `kit/claude/skills/muthur-orchestrate.md` drops the
  "put the three inputs in `--note`" instruction because the prompt now always carries them.
- **Acceptance:** `WorkerContractTests` assert the composed prompt contains the verified block and not the recovery
  text; a `worker run` with a mismatched base still refuses before launch (`ThroughputTests`); sim `contextBytesPerColdStart`
  for implementers drops by at least the size of the removed section.

### U1.4 Stop posting to roles nobody polls
- **Files:** `LifecycleService.ImplementedAsync` (skip the `role:validator` post when the conductor is on; keep it
  when validators are human-staffed), unread-age on the dashboard inbox panel.
- **Acceptance:** `LifecycleTests` both branches.

## 4. Phase 2 — Checks-only validation (the deferred Phase 4 of the conductor tuning)

### U2.1 Parse the spec's Verification
- **Files:** new `src/Muthur.Launch/SpecVerification.cs` (fenced command blocks under `## Verification`, `needs:`,
  `capabilities:`, `work-kind:`, and a new standalone line `validation: checks-only | judgment`), used by
  `Validations.ChecksAsync` so the subject's `RequiredChecks` carries the spec's commands as well as the project's
  build/test; `TaskService` spec set runs the same parser as a lint: no Verification section, or a browser
  requirement without `needs: headless-browser` and probe paths, is a 422 `spec_unverifiable` with the line quoted.
- **Acceptance:** `Muthur.Launch.Tests/SpecVerificationTests` on fixtures including the two historical "needs a live
  browser" specs; `ValidationSubjectTests` see the commands on the subject.

### U2.2 A deterministic validator that takes no seat
- **Files:** `muthur.project.json` gains `checksOnlyValidation: false` (per-project, default off);
  `ConductorService.PlanAsync` (a pending `(task, role)` on a project with the switch on, whose subject declares no
  judgment, goes to a `deterministicVerdicts` list instead of a `ConductorAssignment`), `RunPassAsync` (executes the
  list before sessions: detached worktree at `implementationSha`, run every `RequiredChecks` command through the
  runner `IntegrationRunner` already uses, then `LifecycleService.VerdictAsync` as `Caller.System` with evidence =
  per-command exit codes and output tails, validator identity `deterministic/checks` registered like the integration
  runner).
- **Does:** for the mechanical majority, integration's checks become the verdict, once, before landing; a model
  validator is staffed only when the spec says `validation: judgment` or declares `needs:`. A failed check returns the
  task to its owner with the same evidence shape a model validator would leave.
- **Acceptance:** `ConductorTests` with the fake runner: switch off → session planned; switch on + judgment → session
  planned; switch on + commands only → verdict recorded, no seat used, `validation.passed` by `deterministic/checks`;
  `sim run` with the sim project switched on lands 6 tasks at 1.4 or fewer cold starts per landed task.

## 5. Phase 3 — Route by work-kind, bound by effort and cost

### U3.1 Effort follows work-kind
- **Files:** `RoutingPolicy.EffortFor(workKind, candidate)` (mechanical → low, general → medium, complex-debugging and
  ui-interaction → high; the candidate's `reasoningEffort` is the ceiling), applied in `WorkerCommands.RequestFor` unless
  `--effort` is passed; `WorkerRunReport.ReasoningEffort` already records it.
- **Acceptance:** `WorkerReasoningEffortTests`.

### U3.2 Routing fed from receipts
- **Files:** `RoutingCommands.report` computes the rates it currently zero-fills from the last 14 days of
  `worker.finished/failed` and `validation.failed` events per (harness, model, workKind): done rate, blocked rate,
  false-approval rate (a done unit whose task later failed validation), median seconds, mean `costUsd`;
  `WorkerCommands.Candidates` moves `RecommendedCatalogPosition` to the front when a recommendation exists;
  `docs/routing.md` (promised by T-108, never written).
- **Acceptance:** `RoutingPolicyTests` cost tiebreak; `RoutingTests` end to end with seeded events.

### U3.3 Bounds other than wall clock
- **Files:** `ClaudeAdapter` passes `--max-turns` from the candidate (`maxTurns` in the catalog, default none);
  `MuthurOptions` splits `ConductorSessionMinutes` into orchestrator (45) and validator (30);
  `ConductorService.BudgetBlockedAsync` also blocks a `(task, day)` whose summed `costUsd` from U0.2 exceeds
  `ConductorCostPerTaskDay` (default unset), recording `conductor.budget_blocked { reason: cost }`.
- **Acceptance:** `ConductorBudgetTests`.

### U3.4 Work-kind at intake from the utility tier
- **Files:** `muthur utility classify --task T-n` beside `summarize` (`LocalSummary` pattern: one bounded local

- **Acceptance:** `UtilityCommands` tests with the fake local endpoint; the 99 zero-second utility failures in the

## 8. Phase 5 — pi as a third harness (deferred until Phases 0–4 land)

Kept here so the adapter is designed against the measured baseline rather than guessed.

- **Adapter:** `src/Muthur.Launch/PiAdapter.cs` mirroring `ClaudeAdapter`: `pi --mode json --no-session -na
  --system-prompt <contract file> --tools read,bash,edit,write,grep,find,ls --thinking <effort> --model <provider/id>`
  with the prompt on stdin; usage and cost read from each `message_end` event's `usage` block; a project-local `.pi/`
  extension implements the deny list (`git push`, `git merge`, `gh`, `muthur`) through the `tool_call` hook, generated by
  the launcher the way `claude-settings.json` is today.
- **Where it fits:** implementer and validator tiers, where MUTHUR already owns the worktree and wants no harness
  subagents. Not the mastermind orchestrator.
- **Integration test:** `muthur sim run --implementer pi --model ollama/<local model>`: the same 6-task fixture with the
  scripted orchestrator dispatching real `worker run` units to pi on a local model, one trivial file change per unit.
  Compare against the Phase 4 row: context bytes per cold start, seconds per unit, done/blocked rate, and the cost
  fields U0.1 records. Also run the same units through the Claude and Codex adapters at the same effort for a
  three-way row.
- **Known risks to verify at that time:** no sandbox in pi (the deny extension is the whole boundary); Anthropic
  subscription OAuth policy for third-party harnesses (plan on API keys or a local model); 0.x churn and the
  `@earendil-works` package rename.
