## 1. Rules for this work

- Dogfooding stays paused; work directly on `main`, one branch per phase, one commit per unit, tests beside the
  classes named below. Each phase ends with the sim re-run and its numbers appended to §7.
- Nothing in Contracts/Core/Data/Server names a vendor; token parsing lives in `Muthur.Launch` adapters.
- Every new decision the hub makes on a session's behalf (a deterministic verdict, a refused dispatch, a skipped
  launch) is a ledger event with a stable code. Silence is the failure mode this repo has already paid for.
- Nothing here changes what counts as validated: a checks-only verdict is opt-in per project and only for specs that
  declare no judgment check.

### U1.2 Worker environment preflight
- **Files:** new `src/Muthur.Launch/WorkerEnvironment.cs`; `WorkerCommands.RunAsync` between the spec parse (line ~255)
  and admission; `muthur doctor` gains the same checks.
- **Does:** before any reservation, for the candidate harness, verify deterministically what the 09-21 blocked reports
  named: the worktree's git common dir is writable by the launching identity, `NuGet.Config` and the package cache are
  readable, `TEMP` is writable, `dotnet --version` runs. For Codex this runs under the sandbox identity the adapter will
  use (the probe engine in `CapabilityEvaluator` already knows how to derive it); the result is cached per
  (harness, machine, day) under `MUTHUR_HOME/capabilities` like an observation. A failure refuses with
  `worker_environment_unavailable` naming the path and the identity, records `worker.failed { failureKind: environment }`,
  and starts no model.
- **Investigation result (2026-09-22):** Codex's Windows sandbox (`[windows] sandbox = "elevated"`) runs workers as
  the local users `CodexSandboxOffline`/`CodexSandboxOnline`, both members of the local group `CodexSandboxUsers`.
  Codex itself grants that group read on `%USERPROFILE%\.nuget\packages` and modify on the workspace, but
  `%APPDATA%\NuGet` and `NuGet.Config` carry only SYSTEM, Administrators and the user, so every `dotnet restore`
  in the sandbox fails before compiling. The `.git` directory carries explicit deny entries for the sandbox users
  (Codex's own "keep .git read-only" rule), which is the `ORIG_HEAD.lock` refusal; the launcher already commits
  on the worker's behalf for that case. The fix is a one-time ACL grant, which the preflight prints and `muthur
  doctor` repeats: `icacls "%APPDATA%\NuGet" /grant "CodexSandboxUsers:(OI)(CI)(RX)"`. Built as `WorkerEnvironment`
  (an ACL read, no cache needed at that cost) and applied in `worker run` before admission and in the doctor.
- **Acceptance:** `Muthur.Launch.Tests/WorkerEnvironmentTests` with a fake process runner; `WorkerAdmissionTests`:
  a failing preflight reserves no seat.

## 9. Phase 6 — pi onto the implementer tier, judged on fresh tokens (planned 2026-09-23)

Why this order: the pi row beat the Codex local-provider row on every axis that matters (2 of 2 landed, 6 min,
10 model-minutes), and its token number splits into 172 K fresh and 1.7 M cache reads. Cache reads are what a hosted
provider bills at a tenth (Anthropic) or a quarter (OpenAI) of fresh input, and what a local model pays for in
minutes, so "fresh tokens per landed task" is the number this phase optimises, with cache reads and minutes read
alongside. The blocker to using any of it on the live hub is that pi has no sandbox: `SessionCommands.Denied` is
enforced by Claude's settings file and Codex's sandbox, and by nothing at all in pi.

### U6.1 The deny list becomes a pi extension (the gate)
- **Files:** `PiAdapter.Build` writes `<scratch>/pi-guard.ts` and passes `-e <path>` (explicit `-e` paths load even
  under `--no-extensions`, per `docs/cli.md`); new `PiGuard.Extension(request)` renders it: a `tool_call` handler
  that returns `{ block: true, reason }` for a `bash` call whose command matches any `DeniedCommands` glob
  (`git push*`, `git merge*`, `gh*`, and `muthur*` for workers, as `WorkerRequest.DeniedCommands` already lists)
  and for `write`/`edit` under `.git/` (the example `protected-paths.ts` shape). Anchored at the command's start and
  after `&&`, `;`, `|`, so `echo x && git push` is caught. `CapabilitySettings` for pi hashes the rendered guard the
  way `ClaudeAdapter` hashes its settings so a changed deny list invalidates the capability cache.
- **Acceptance:** `Muthur.Launch.Tests/PiAdapterTests`: the invocation carries `-e` and the rendered extension
  names every denied pattern; a rendered guard for a request with no denials registers no handler. The capability
  probe (`CapabilityEvaluator`) gains a pi row that runs `git push --dry-run` inside a session and expects the block
  message in the event stream, so `muthur doctor` proves the guard once per (machine, day) before any live seat.
- **Not in scope:** filesystem containment beyond the worktree; pi's own docs say a container is the only strong
  boundary. The live-hub rule stays: pi takes implementer and validator seats, never the orchestrator's.

### U6.2 One accounting for three harnesses
- **Files:** `CodexAdapter` parses `--json` `token_count` events (input, cached input, output) instead of the
  `tokens used` line, so its row carries `CacheReadTokens` like the others; `SessionReceipts`/`ReceiptsService`
  sum fresh (input + output) and cache-read per task and per (harness, model) and `muthur receipts --task` prints
  both; the sim report's `modelTokens` splits into `freshTokens` and `cacheReadTokens` for every harness and gains
  `freshTokensPerLanded`.
- **Acceptance:** `HarnessTests` fixtures for the Codex JSON stream; `ReceiptsTests` two harnesses, one task;
  `SimCommandTests` new fields. The Codex local-provider row in §8 is then re-run once so the comparison is
  like for like (its 1.24 M "total" is presumed to be mostly cache reads; this settles it).

### U6.3 Trim what pi hands the model
- **Files:** `PiAdapter.Build` passes `--tools` per tier (implementer and orchestrator: `read,bash,edit,write,grep,find,ls`;
  validator: `read,bash,grep,find,ls`) and `--system-prompt <scratch>/pi-system.md`: a MUTHUR-minimal prompt
  (role, worktree, the verified-by-launcher block, the deny list in words) in place of pi's default, whose
  1,400 tokens are the floor today; the scratch catalog's `contextWindow` follows the catalog candidate
  (`contextWindow` key, default 32768) so a 26b model on a 64 K window is not compacted at 32 K.
- **Acceptance:** `PiAdapterTests` argument sets per tier; the 2-task sim re-run on gemma4:26b shows the first
  implementer unit under 6.8 K fresh tokens and the orchestrator sessions under 140 K fresh in total.

### U6.4 pi in the catalog and the sim's three-way row
- **Files:** `HarnessDefaults.CatalogJson`: `implementer` gains `{ "harness": "pi", "model": "anthropic/<model>", "account": "anthropic-api", "enabled": false }`
  and `local-implementer` gains `{ "harness": "pi", "model": "gemma4:26b", "account": "local", "enabled": false }`;
  `DoctorHarnessCheck` knows `pi`; `muthur sim run --harness pi --model <hosted>` runs with the user's own pi

- **Acceptance:** `RoutingTests` a disabled candidate is never staffed; a `worker run --harness pi` on the sim

- **Decision the row answers:** whether pi takes the hosted implementer seat by default (cheaper per landed unit
