# Capability-probe admission

T-113 supplies reservations and a launch lifetime wrapper. It does not implement a capability engine or enable production probing. T-100 must obtain admission through this contract before its first authorized observation. No actual probes were run for T-113; the actual-probe sample count is zero. Fixture callbacks and scratch API reservations are not real-use evidence.

`POST /api/v1/workers/probes/admit` accepts `ProbeAdmissionRequest(Task, Tier, Harness, Model, Account, RunId)`. All identifiers must be nonempty; `RunId` must be a GUID in N format. The exact tier/harness/model/account must already exist in the current catalog. The caller must be the registered mastermind owning the in-progress task, or Founder. Admission checks the current account limit, conductor switch and ceiling, and the task's rolling daily `#orchestrator` budget. A probe consumes one additional slot; its conductor orchestrator still consumes its own slot.

The response is `ProbeAdmissionDto(ReservationId, Task, RunId, MayExecute)`. Only the first successful response grants `MayExecute=true`. Identical owner/run/input replays return the original reservation with `MayExecute=false`, even after release. A replay must never launch or release: the original invocation may still be running. Different inputs with the same run ID fail with `probe_run_conflict`; cross-owner requests are unauthorized. A lost first response is not permission to retry execution.

`POST /api/v1/workers/probes/release` accepts `ProbeReleaseRequest(ReservationId)`. Only the original caller identity or Founder can release, including after task ownership changes. Releasing an already released owned reservation succeeds without another event; an unknown ID returns `not_found`. Release does not refund a daily attempt. The reservation and release are durable ledger events, `worker.probe_admitted` and `worker.probe_released`. Conductor status includes active reservations with role `#capability-probe:<reservationId>`.

Refusals include `probe_capacity_exhausted`, `probe_budget_exhausted`, `probe_account_limited`, `probe_candidate_unavailable`, `probe_admission_disabled`, and `probe_run_conflict`. Malformed fields fail `probe_request_invalid`; authorization uses `unauthorized`. Existing daily-budget reset semantics remain shared with conductor staffing.

`Muthur.Launch.ProbeReservationRunner` uses `IProbeAdmissionClient.AdmitAsync` and `ReleaseAsync`. Its generic `RunAsync` obtains admission before invoking the callback, executes exactly once unless the caller is already cancelled after admission, and releases in `finally` after confirmed cleanup. Cancellation after a successful admission releases without invoking the callback; replays never invoke or release. The callback must bound execution and complete process-tree cleanup before returning or throwing an ordinary exception, including cancellation. If cleanup cannot be confirmed, the callback throws `ProbeCleanupUncertainException`; the runner skips release and throws `InvalidOperationException` naming the reservation as retained pending confirmed process cleanup, with the original exception as its inner exception. Release uses a separate ten-second cancellation budget. Release failure names the reservation for recovery; simultaneous callback and release failures are preserved in an `AggregateException`. The CLI's internal `ProbeAdmissionClient` uses `HubClient` and source-generated JSON. This adapter is available for T-100 integration; there is no production probe command.

Reservations survive restart, task completion, lease expiry, and elapsed time. There is no TTL reclamation. After a hard crash or uncertain cleanup, retain the reservation until the original owner or Founder confirms the process tree is gone and explicitly releases it. A callback unable to establish cleanup must throw `ProbeCleanupUncertainException` so it can exit within its execution bound while retaining the reservation for explicit owner or Founder recovery. The wrapper does not loop or retry. This seam does not demonstrate hard-crash process cleanup. A failed release is retried explicitly by reservation ID, never by launching again.
